# Weport v0.9.6 reference-study ledger

This ledger records the read-only reference work required by the v0.9.6
requirements marked `***`. Reference code and assets remain design evidence;
none are shipped or imported into the build.

## Export selection and performance (`***`)

- References studied: `reference-projects/CipherTalk` export picker,
  utility-process and work-pool patterns; `reference-projects/WeFlow` export
  worker/orchestrator and progress handling.
- Adopted: virtualized session selection, explicit selected-session scope,
  bounded worker-pool scheduling, resumable pause/cancel state, and separate
  progress/failure accounting.
- Rejected: copying CipherTalk's utility-process architecture or introducing
  `worker_threads`/stdio transport. Weport's WCDB host must remain the named
  `WeFlow` subprocess using Node IPC.
- Weport deviation: session and media work share a limiter so concurrency does
  not multiply native database and filesystem pressure; main IPC validates IDs
  against the current session list.

## Analytics and ranking

- Reference studied: `reference-projects/WeFlow` analytics pages and report
  chart utilities.
- Adopted: measured plot sizing, value-sensitive color ramps, compact report
  navigation, and accessible control patterns.
- Rejected: radar-based 交流画像, fixed-width sparse bars, and nested report
  navigation that hides annual/dual reports.
- Weport deviation: four direct hub cards and a shared React sizing helper are
  integrated into the existing ECharts theme and responsive layout.

## Word cloud (`***`)

- References studied: `reference-projects/WeFlow` analytics and
  `ReportWordCloud.tsx`; `reference-projects/AnnualReport` ECharts word-cloud
  implementation.
- Adopted: measured responsive stages, frequency-based visual hierarchy,
  hover/focus affordances, and deterministic screenshot-safe rendering.
- Rejected: random placement, raw protocol/XML tokenization, noisy bigrams,
  and a cramped non-interactive ECharts cloud.
- Weport deviation: tokenization is shared by the main-process analytics
  service and the React cloud uses collision-aware deterministic placement with
  a list fallback.

## WeportAI provider profiles (`***`)

- References studied: provider/catalog/base/settings patterns in
  `reference-projects/CipherTalk`; official provider documentation for
  [OpenAI models](https://platform.openai.com/docs/api-reference/models/object?lang=curl),
  [Anthropic model listing](https://docs.anthropic.com/en/api/models-list),
  [OpenCode providers](https://opencode.ai/docs/providers), and
  [OpenCode Zen](https://opencode.ai/docs/zen).
- Adopted: provider catalog plus protocol adapters, explicit model discovery,
  classified failures, profile activation, and masked renderer summaries.
- Rejected: exposing API keys to renderer responses, silently saving profiles
  when discovery fails, or assuming every provider is OpenAI-compatible.
- Weport deviation: complete profile blobs are safeStorage-encrypted in the
  main process, legacy DeepSeek settings migrate in place, and local providers
  may omit an API key while custom providers own their base URL/protocol flow.

## Anti-revoke queue and QA

- Reference studied: Weport's existing WCDB trigger and database-monitor
  pipeline, with WeFlow's session-level trigger behavior as the compatibility
  baseline.
- Adopted: debounced, deduplicated background batching and missing-trigger
  checks.
- Rejected: polling, per-message awaited installation, binary patching, and
  `RevokeMsgPatcher`.
- Weport deviation: only groups first observed after activation are queued;
  existing groups remain under manual control.
