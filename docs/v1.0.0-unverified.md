# Weport v1.0.0 — what could NOT be verified

This build was produced and verified on a **Windows x64** host only. Everything below is
either (a) code that only executes on another platform, or (b) a claim that needs a real
provider, a real WeChat install, or hardware this machine does not have.

**Read this before shipping.** Nothing in this file should be presented to users as tested.

## 1. macOS — nothing runtime was executed

Every macOS code path below was written from source reading and external evidence. **None of it
ran.** There is no Mac in this environment.

| Area | What was changed | Why unverified |
|---|---|---|
| Bundle sealing (#18) | `identity: "-"`, seal-only verification gate, `get-task-allow` removed | Needs `codesign`/`spctl` on macOS. The gate itself (`scripts/verify-mac-pack.sh`) also only runs on a macOS runner. |
| Zip round-trip | gate re-verifies the unzipped app | `unzip` does not propagate `com.apple.quarantine`, so the Gatekeeper "damaged" path a user actually hits is **not** exercised by the gate. |
| Notarization | not attempted (decision: ad-hoc only) | Requires a paid Apple Developer account. Ad-hoc signatures can never be notarized. |
| Data directory resolution | `getDefaultPath()` now validates candidates; WeChat 3.x layouts rejected | Needs a Mac that has been upgraded from WeChat 3.x to confirm `2.0b4.0.9` is really present and really rejected. |
| TCC / Full Disk Access | diagnostic path identified | Needs macOS 14+ to reproduce the permission prompt. |
| Key capture | preflight capability report described | `task_for_pid` behaviour against a real hardened WeChat was not reproduced; the mechanism is established from Apple's own documentation and multiple third-party measurement reports, not from this machine. |
| WCDB host on a read-only install | `Contents/MacOS/WeFlow` + symlinked `Frameworks` | **Must be tested by launching from inside the mounted DMG.** The failure this fixes only occurs there. |
| Image key (`kvcomm`) | unchanged behaviour, warn-then-confirm instead of blocking | Needs a Mac with WeChat 4.x data. |

**Minimum macOS acceptance run** (needs one Apple Silicon Mac, macOS 15+, WeChat 4.x):

```bash
APP="/Applications/Weport.app"
ls -la "$APP/Contents/_CodeSignature/"                      # must contain CodeResources
codesign --verify --deep --strict --verbose=2 "$APP"        # must pass
codesign -dv --verbose=4 "$APP" | grep -E 'Format|Sealed Resources'
ls ~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/   # all_users/ Backup/ <account>/
# then: launch the app from inside the mounted DMG and confirm the DB still connects
```

## 2. Linux — not executed

The Linux key helper, AppImage host fallback and XDG autostart were not touched, but they were
also not re-verified after the `wcdbHostClient` change (which added a macOS-only branch ahead of
the existing copy fallback). The Linux path is unchanged in behaviour but shares the function.

## 3. Provider behaviour — no credentials were used

- No authenticated request was made to **any** provider. OpenCode Go / DeepSeek / OpenAI /
  Anthropic behaviour is taken from published documentation, the models.dev payload, and the
  recorded probes in `docs/reference/` — not from a live round trip.
- **Per-model protocol routing** resolves through a three-layer chain (model → provider →
  profile). It is unit-tested against the shipped models.dev snapshot (860 models), but the
  routing decision was never confirmed against a real gateway response.
- **models.dev** is fetched at runtime and is MIT-licensed, but its **data-usage terms are
  undocumented** (upstream issue #1639). It is used as a cache only, never shipped as a fork,
  and is attributed in `THIRD-PARTY-NOTICES.md`. If that posture is unacceptable, remove the
  registry refresh — the bundled snapshot alone is sufficient offline.
- The bundled snapshot is a point-in-time capture. With no network on a first launch the UI will
  show its prices, labelled `元数据 bundled`.

## 4. Cache hit rate — the number is a projection, not a measurement

`electron/services/ai/cacheHarness.test.ts` proves the **necessary condition** (byte-identical
prefixes, only appended) over a simulated 200-step run, and projects >99% from those token
economics. It does **not** measure real cache behaviour; that depends on the provider.

The real measurement is `node scripts/verify-cache-prefix.mjs`, which reads the
`kind:"prefix"` records the main process writes to `weport-ai/debug.log`. **Run it after a long
real conversation** — it has not yet been run against v1.0 data, because doing so requires an
authenticated multi-turn conversation through the new harness, which was never performed.

## 5. WeChat data paths

- The Windows `%APPDATA%\Tencent\xwechat\radium\users\<hash>` relocation appears in **one
  uncorroborated internal note**; it was not implemented, only noted.
- `key_info.db` **is** now used (see `docs/v1.0.0-audit.md`) — and the research that recommended
  it needed correcting: the table stores `md5(wxid)`, not the wxid, so it cannot enumerate
  accounts. The canonical wxid comes from the `all_users/login/<wxid>` **directory name**, which
  was verified against real data on this machine. Only the `_<4 hex>` suffix ambiguity is
  untested at scale.
- Export behaviour was exercised only through demo data in the screenshot harness, not against a
  real account with real media in this build.

## 6. Not implemented at all

- OS-level scheduling outside the app (Task Scheduler / launchd / systemd) — WeBot runs only
  while the Weport tray process is alive. **If the user fully quits Weport, scheduled tasks do
  not fire**, and are caught up per each task's policy on the next launch.
- Apple notarization, Intel Mac support, and rebuilding the macOS native artifacts.
- A long-run soak test. The app was verified by build + tests + the 19-capture harness, not by
  hours of continuous use with real data.
- **WeClone is present** (restored from `9669dcb`, `manage` / `create` sections wired) but only
  the hub entry screen was reviewed visually. The `manage` and `create` sections have never been
  rendered on screen in this build, and no clone was ever generated — the generation path needs a
  real provider key and a real account.

## 7. UI redesign — what the harness does and does not prove

Every page now has a screenshot, and the harness asserts each one is non-blank, that the
navigation rail keeps its labels, that nothing overflows horizontally at 986px and 1426px of
viewport, and (for WeBot) the actual measured card/title widths and column counts.

What it does **not** prove:

- **No control was actually clicked through** except the ones the captures drive (tab switches,
  the WeBot editor, the settings category nav). The MCP "copy client config" button, the
  appearance sliders, the new settings panes' actions and the SNS toolbar buttons were rendered
  but not exercised. `api.mcp.getClientConfig()` was never called on a real install.
- **The MCP panel reads `未运行` in the screenshot harness** because the harness instance cannot
  bind 5032 while the installed Weport is running. The "running" branch of that panel has only
  been seen in code.
- **Breakpoints were measured at two widths** (986px and 1426px CSS). The behaviour between and
  outside them — in particular the 640px container query that stacks the WeBot form — is
  reasoned from the measured container widths, not observed.
- **No real user has used any of it.** The redesign is judged from screenshots and geometry, so
  "is it actually clearer" remains an open question that only the user can answer.
