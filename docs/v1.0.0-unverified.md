# Weport v1.0.0 — what could NOT be verified

This build was produced and verified on a **Windows x64** host only. Everything below is
either (a) code that only executes on another platform, or (b) a claim that needs a real
provider, a real WeChat install, or hardware this machine does not have.

**Read this before shipping.** Nothing in this file should be presented to users as tested.

## 1. macOS — nothing runtime was executed

Every macOS code path below was written from source reading and external evidence. **None of it
ran.** There is no Mac in this environment.

| Area | What was changed | Why unverified |
|---|---|---|
| Bundle sealing (#18) | `identity: "-"`, seal-only verification gate, `get-task-allow` removed | Needs `codesign`/`spctl` on macOS. The gate itself (`scripts/verify-mac-pack.sh`) also only runs on a macOS runner. |
| Zip round-trip | gate re-verifies the unzipped app | `unzip` does not propagate `com.apple.quarantine`, so the Gatekeeper "damaged" path a user actually hits is **not** exercised by the gate. |
| Notarization | not attempted (decision: ad-hoc only) | Requires a paid Apple Developer account. Ad-hoc signatures can never be notarized. |
| Data directory resolution | `getDefaultPath()` now validates candidates; WeChat 3.x layouts rejected | Needs a Mac that has been upgraded from WeChat 3.x to confirm `2.0b4.0.9` is really present and really rejected. |
| TCC / Full Disk Access | diagnostic path identified | Needs macOS 14+ to reproduce the permission prompt. |
| Key capture | preflight capability report described | `task_for_pid` behaviour against a real hardened WeChat was not reproduced; the mechanism is established from Apple's own documentation and multiple third-party measurement reports, not from this machine. |
| WCDB host on a read-only install | `Contents/MacOS/WeFlow` + symlinked `Frameworks` | **Must be tested by launching from inside the mounted DMG.** The failure this fixes only occurs there. |
| Image key (`kvcomm`) | unchanged behaviour, warn-then-confirm instead of blocking | Needs a Mac with WeChat 4.x data. |

**Minimum macOS acceptance run** (needs one Apple Silicon Mac, macOS 15+, WeChat 4.x):

```bash
APP="/Applications/Weport.app"
ls -la "$APP/Contents/_CodeSignature/"                      # must contain CodeResources
codesign --verify --deep --strict --verbose=2 "$APP"        # must pass
codesign -dv --verbose=4 "$APP" | grep -E 'Format|Sealed Resources'
ls ~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/   # all_users/ Backup/ <account>/
# then: launch the app from inside the mounted DMG and confirm the DB still connects
```

## 2. Linux — not executed

The Linux key helper, AppImage host fallback and XDG autostart were not touched, but they were
also not re-verified after the `wcdbHostClient` change (which added a macOS-only branch ahead of
the existing copy fallback). The Linux path is unchanged in behaviour but shares the function.

## 3. Provider behaviour — no credentials were used

- No authenticated request was made to **any** provider. OpenCode Go / DeepSeek / OpenAI /
  Anthropic behaviour is taken from published documentation, the models.dev payload, and the
  recorded probes in `docs/reference/` — not from a live round trip.
- **Per-model protocol routing** resolves through a three-layer chain (model → provider →
  profile). It is unit-tested against the shipped models.dev snapshot (860 models), but the
  routing decision was never confirmed against a real gateway response.
- **models.dev** is fetched at runtime and is MIT-licensed, but its **data-usage terms are
  undocumented** (upstream issue #1639). It is used as a cache only, never shipped as a fork,
  and is attributed in `THIRD-PARTY-NOTICES.md`. If that posture is unacceptable, remove the
  registry refresh — the bundled snapshot alone is sufficient offline.
- The bundled snapshot is a point-in-time capture. With no network on a first launch the UI will
  show its prices, labelled `元数据 bundled`.

## 4. Cache hit rate — the number is a projection, not a measurement

`electron/services/ai/cacheHarness.test.ts` proves the **necessary condition** (byte-identical
prefixes, only appended) over a simulated 200-step run, and projects >99% from those token
economics. It does **not** measure real cache behaviour; that depends on the provider.

The real measurement is `node scripts/verify-cache-prefix.mjs`, which reads the
`kind:"prefix"` records the main process writes to `weport-ai/debug.log`. **Run it after a long
real conversation** — it has not yet been run against v1.0 data, because doing so requires an
authenticated multi-turn conversation through the new harness, which was never performed.

## 5. WeChat data paths

- The Windows `%APPDATA%\Tencent\xwechat\radium\users\<hash>` relocation appears in **one
  uncorroborated internal note**; it was not implemented, only noted.
- `key_info.db` **is** now used (see `docs/v1.0.0-audit.md`) — and the research that recommended
  it needed correcting: the table stores `md5(wxid)`, not the wxid, so it cannot enumerate
  accounts. The canonical wxid comes from the `all_users/login/<wxid>` **directory name**, which
  was verified against real data on this machine. Only the `_<4 hex>` suffix ambiguity is
  untested at scale.
- Export behaviour was exercised only through demo data in the screenshot harness, not against a
  real account with real media in this build.

## 6. Not implemented at all

- OS-level scheduling outside the app (Task Scheduler / launchd / systemd) — WeBot runs only
  while the Weport tray process is alive. **If the user fully quits Weport, scheduled tasks do
  not fire**, and are caught up per each task's policy on the next launch.
- Apple notarization, Intel Mac support, and rebuilding the macOS native artifacts.
- A long-run soak test. The app was verified by build + tests + the 22-capture harness, not by
  hours of continuous use with real data.
- **WeClone is present** (restored from `9669dcb`, `manage` / `create` sections wired) and both
  sections now have screenshots, but no clone was ever generated — the generation path needs a
  real provider key, a real account and a running WeClone server.

## 7. UI redesign — what the harness does and does not prove

Every page now has a screenshot, and the harness asserts each one is non-blank, that the
navigation rail keeps its labels, that nothing overflows horizontally at 986px and 1426px of
viewport, that the WeBot task card and editor keep measured widths and column counts, that the
WeportAI middle column never drops below 300px, and that no screen shows `undefined` / `NaN` /
`[object Object]`.

What it does **not** prove:

- **No control was actually clicked through** except the ones the captures drive (tab switches,
  the WeBot editor, the settings category nav, the WeClone hub cards, the analytics entries and
  the dual-report friend picker). The MCP "copy client config" button, the appearance sliders, the
  SNS toolbar buttons and the antirecall install/revert buttons were rendered but not exercised.
  `api.mcp.getClientConfig()` was never called on a real install.
- **The MCP panel reads `未运行` in the screenshot harness** because the harness instance cannot
  bind 5032 while the installed Weport is running. The "running" branch of that panel has only
  been seen in code.
- **The placeholder scan only looks for three tokens.** `undefined`, `NaN` and
  `[object Object]` — a screen can still show a wrong number, or `0` where a value failed to
  load, and pass. The dual report was doing exactly that (a wall of zeros) until it was given
  demo data.
- **Breakpoints were measured at two widths** (986px and 1426px CSS). The behaviour between and
  outside them — in particular the 640px container query that stacks the WeBot form — is
  reasoned from the measured container widths, not observed.
- **The analytics reports were only ever rendered against demo data.** The `dualReport` worker
  runs against a real database that the harness does not have; a populated report is now captured,
  but through a demo override, not through the worker.
- **No real user has used any of it.** The redesign is judged from screenshots and geometry, so
  "is it actually clearer" remains an open question that only the user can answer.

## 8. Round-16 UI pass — what is still only reasoned

The 导出数据 / 朋友圈 / 外观 / 设置 changes in this round were verified by screenshots at the
app's default window size (about **1060 × 635 CSS px** on this host — Windows 150% scaling, so
the 1599px captures are 1.5× device pixels). Consequences worth knowing:

- **The two-column export layout only appears at ≥1280 CSS px of viewport.** At the default
  window the page is single-column by design; the ≥1280 branch has been rendered only in the
  harness's 1426px probe, not in real use.
- **The wheel-zoom lightbox is asserted by code review and by the DOM**, not by a scripted
  pointer gesture: the harness captures screenshots and probes geometry; it does not dispatch
  wheel events. The anchored-zoom maths (transform-origin 0 0 + translate, origin recovered
  from `getBoundingClientRect() - offset`) is therefore unexercised.
- **`font-synthesis-weight: none`** was chosen because the shipped Weport font (仓耳渔阳体 W03)
  carries only a Regular face and no GSUB/GPOS. The before/after difference is visible in
  side-by-side crops of the 朋友圈 statistics row, but a full visual regression pass over every
  screen at every theme has not been done.
- **The 用色浓度 (accent strength) axis is applied to a fixed list of surfaces** (panels, post
  cards, `v09` panels at `vivid`). Charts read the same tokens, so they follow, but no chart was
  captured at all three strengths.
- **删掉 `font-variant-numeric: tabular-nums`** globally is a workaround, not a fix: the real
  cause is that the bundled font has no `tnum` feature, so the declaration made Chromium pick a
  fallback face for digits. If a future font ships real figures, the property can come back.
- **The 朋友圈 author-popup and delete-confirm overlays** were already closing on backdrop click;
  what changed is the lightbox (which swallowed those clicks) and the calendar popover (which had
  no outside-click dismissal). Both are verified from source, not from click automation.
- **No print/export regression run** was done after the export page restructure: the export
  writer was not re-exercised against a real database in this round, only the page's rendering.

# Round 17 — Stage 2 (connectors, TUI, WeClone, cache)

Everything in this section was measured on 2026-09-13 against the installed v1.0.0 build,
except where a line says otherwise.

## What is now measured, not asserted

- **Todoist connector, live.** A real token created a real task on the user's account and it
  read back with the natural-language due date parsed by Todoist (`tomorrow 9am` →
  `Sep 14 9:00 AM`) and the priority intact (`urgent` → `urgent`, which is the round trip
  that catches the inverted scale). Command: `scripts/verify-todoist-connector.mjs --create`.
- **The whole TUI path.** `weport connectors.addTask content=… dueText=tomorrow\ 10am
  priority=medium` went through the terminal → JSON-RPC → the service layer → Todoist and
  returned the created task. That is the end-to-end proof that the TUI is a real client.
- **Provider configuration.** One profile only, `opencode-go` / `deepseek-v4.1-flash`,
  assigned to chat, weclone and webot; `ai.status` read from the installed app confirms it.
- **Multi-turn prompt cache** (6 turns, tools attached): per-turn 96.2 / 96.9 / 98.1 / 97.5 /
  96.9 / 98.0 %, steady state **97.4 %**, and `prefix` debug records show `append` on every
  turn with an unchanged prefix hash — i.e. nothing is rewritten mid-conversation.

## The cache number is 97.4 %, not 98 % — why, and what would move it

The miss is **not** prefix instability. `scripts/verify-cache-prefix.mjs` and the AI debug log
(`{userData}/weport-ai/debug.log`, `kind:"prefix"`) both show the frozen prefix (system prompt
+ 17 tool definitions) hashing identically across turns. The miss is the *new tokens added
since the last request*: each turn appends the previous prompt, the previous answer, and the new
question, and a provider can only cache what it has already seen. With ~7 k tokens of context
and ~70–120 tokens appended per turn, the ceiling is roughly 1 − (new/seen), which lands
at 97–98 %.

So 98 %+ on a short conversation requires either a much larger frozen prefix (the tools and
system prompt dominate today at ~6.8 k of the 7.0 k first-turn prompt) or accepting that the
first turn of every conversation is a cold miss. What is verified is the invariant that matters:
the prefix never changes for reasons under Weport's control. A long session (50+ turns) is the
honest test of the 98 % claim and has not been run.

## WeClone: what was wrong, and the measured effect of fixing it

The clone on disk predated the current pipeline and had three defects that cap reply quality
regardless of model:

1. its corpus mixed the user's lines with the other party's, plus raw `<msg>` XML;
2. the sheets it uploaded were **LLM summaries**, so the identifying phrasing had been
   rewritten by another model;
3. nothing distinguished register (group vs DM, language mix, length band).

`scripts/build-weclone-voice.mjs` rebuilds the corpus from the real message store: only the
user's own messages, media/XML/system lines dropped, split into
`[what they replied to] → [what they actually said]` episodes carrying a register tag, and the
style sheet is computed from the corpus (median length 12 chars, 79.6 % lowercase English,
1.16 punctuation per 100 chars) instead of being generated.

Measured on the **same 20 held-out turns**, through the same server and model:

| corpus + prompt | lexical (dice bigram) | length ratio | lowercase delta | punctuation delta | latency |
| --- | --- | --- | --- | --- | --- |
| legacy chunks + raw prompt | 0.036 | 3.98 | 0.060 | 0.294 | 5397 ms |
| voice episodes + same prompt | **0.287** | **1.59** | **0.012** | **0.000** | **3205 ms** |

Every axis moves the right way: 8× closer lexically, output length within 1.6× of the real
person instead of 4×, and register drift near zero. What has *not* been done: the server-side
prompt and retrieval were left untouched, so the 0.287 is a floor, not a ceiling, and the
evaluation set is drawn from conversations the corpus also contains — it measures imitation
fidelity, not generalisation to unseen conversations.

## Still unverified after this round

- **The 98 % cache claim on a long session** (see above).
- **WeClone inside the app**: the server is verified directly, but the app→server path
  (`weCloneServerUrl` + owner token in 设置 → 人格克隆) has not been exercised, so the
  in-app upload/chat buttons remain unproven.
- **The connector's agent tool** (`create_connector_task`) is wired and unit-tested at the
  command layer, but no WeportAI run has been observed calling it end to end.
- **TUI layout at other sizes**: frames were verified at 140×38 and nothing else; no very
  narrow (80×24) run, and no interactive keystroke test (the harness renders frames, it does
  not drive the keyboard).
- **The TUI is not yet an installable npm package**: it builds and runs from the repository
  (`packages/weport-tui`, `npm run build:tui`), but `npm publish`-ready packaging — a wrapper
  that locates the engine on each platform — is still open.
