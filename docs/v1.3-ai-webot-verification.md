# V1.3 live DeepSeek and WeBot verification

> Historical foundation receipt from before the feature implementation. See [current implementation status](v1.3-implementation-status.md) for later changes and remaining acceptance.

Executed on Windows x64, 20 October 2026, on `codex/v1.3`. This verifies the current AI/automation foundation; it does not implement the proposed evidence-linked memory or delta-digest architecture.

## Credential and data handling

The harness reused the user's configured DeepSeek profile, model `deepseek-flash`, through the normal `ConfigService` and provider assignment APIs. The saved provider credential envelope was encrypted at rest. The harness copied the encrypted configuration and Chromium `Local State` into a private profile; the application decrypted the credential internally. No raw API key, authorization header, or key hint was returned to the agent, printed, or written into the receipt. No direct key extraction was needed.

The user explicitly authorized real-model requests with real chat history. Selected message text was therefore transmitted to the configured DeepSeek endpoint by the normal application provider. Private profiles used a stable, verified DB/WAL copy, an isolated AI workspace/export directory, and disabled connectors, notification monitoring, autostart and HTTP/MCP servers. The original WeChat process remained running. Original configuration/Local State hashes were unchanged. Temporary copied databases, credentials, AI transcripts, notes, and exported/private data were deleted after each run.

## Reproduce

```powershell
node scripts/verify-v13-ai-webot-real.mjs
```

The harness uses `release/win-unpacked/Weport.exe`, a private offscreen Electron instance, and only presence/model metadata from the provider summary. It explicitly assigns the DeepSeek profile to both `chat` and `webot` in the private configuration. Model calls have bounded investigation prompts and an abort deadline.

Sanitized receipt: `%TEMP%/weport-v13-ai-acceptance/result.json`. Previous receipts are retained as `prior-*.json`. They contain statuses, tool names, output hashes, language/timestamp/count checks and cleanup results, not message bodies, contact names, account IDs, keys, or model reasoning. A sanitized console log for the completed seven-run acceptance is `%TEMP%/weport-v13-ai-final.log`.

## Completed live cases

The seven-run acceptance completed with `ok=true`, `realProfileUnchanged=true` and `privateCleanupVerified=true`:

| Case | Actual execution | Verified result |
| --- | --- | --- |
| AI English | Normal AI chat, real history | Nonempty English answer, fresh sync, actual session read, requested 12-message window, returned count and newest source timestamp included |
| AI Chinese | Same chat, language switched | Chinese answer and same factual/tool checks |
| AI English again | Same chat switched back | English answer and same factual/tool checks |
| WeBot English | Real `runNow` dispatch through production AI service | Successful run, one stored note, automatic-task label and factual/tool/language checks |
| WeBot Chinese | Real `runNow` dispatch | Same checks in Chinese |
| Timed WeBot English | Enabled interval task; actual scheduler fired, no `runNow` | Exactly one completed successful run and note; factual/tool/language checks |
| Timed WeBot Chinese | Enabled interval task; actual scheduler fired | Same checks in Chinese |
| Process restart | Closed/reopened the private Electron process | All four WeBot task/note pairs persisted |

Timer tests arm an interval schedule 15 seconds ahead with a one-hour recurrence, wait for the real scheduler/dispatcher to finish, then disable that test task. No recurring test tasks were added to the user's normal profile. The three interactive turns share one AI conversation; each automation has its own invocation metadata.

The test's independently read 12-message source window belongs to one real conversation, selected without printing its identity or contents. Each answer is checked for the expected language, explicit returned message count, exact maximum source timestamp, and tool evidence of `sync_chat_history` and `read_session_messages` with the requested session/limit/offset. Receipts also record whether a read targeted a different conversation. These checks establish bounded factual recall and language switching, not the correctness of every interpretive observation.

## Harness corrections and limits

The first timestamp oracle incorrectly treated row zero as the newest message. `ChatService` normalizes the selected native page into ascending display order; the newest timestamp in that page is its maximum. Diagnostic receipts showed DeepSeek selected that maximum correctly. The oracle was corrected; these initial failed assertions are not evidence of a model regression.

The first timer wait also resumed before a completed run was available. It was replaced with explicit Node-side polling of persisted run status. Both a timer-only run and the subsequent full seven-run acceptance passed. No scheduler production change was made for that harness error.

The receipt explicitly leaves `groundedSummaryManuallyReviewed=false`: no claim is made that the free-form observations were independently adjudicated, that every answer met the requested word/character budget, or that relationship interpretations are correct. Scope adherence in these selected prompts is not service-enforced per-task authorization. Actual account switching could not be tested with a second real account.

Still unimplemented/unaccepted: structured clickable source citations, account-scoped AI memory, claim/counterevidence records, durable last-success digest watermarks, idempotent digest publication, configurable run spending limits, and deterministic no-change suppression. Current successful runs create a note and notification; this is not acceptance of the proposed quieter delta-digest behavior.

Deterministic unit coverage separately exercises scheduler catch-up and date boundaries, cancellation, late dispatch results, error runs, transcript replay and prompt language policies. A short live run does not establish day-long scheduling or memory stability. Native macOS/Linux, QR login capture, and live desktop glass were not exercised by this module.

The complete live suite ran on fresh packaged payload SHA-256 `9a0835066238a5c3064153caec7d0316271b523e020ee9204fd821cbc1913312`. A subsequent export-only correctness fix requires its own fresh archive/package acceptance; it does not change the tested AI/provider/scheduler implementation.
