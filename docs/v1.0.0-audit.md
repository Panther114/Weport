## Fixed in this sweep

**`dbPathService.autoDetect()` reported a permissions problem as "not found".**
When every candidate directory failed validation it returned one generic message. But on
macOS 14+ there is a completely different cause with the same symptom: the directory exists and
the process simply cannot read it (no Full Disk Access). The user's natural response — re-check
the path — is the wrong action, and nothing in the message hinted otherwise.
`findUnreadableCandidate()` now distinguishes `EPERM`/`EACCES` and names the fix.

## Resolved during this sweep: the `key_info.db` account oracle

Originally listed here as "cannot be implemented safely without a real machine to verify on".
That turned out to be wrong — **the data was on this machine all along**, and reading it
corrected the research:

- `D:\xwechat_files\all_users\login\<wxid>\key_info.db` exists, is **plaintext SQLite**
  (`SQLite format 3\0`) while the chat databases are encrypted. Its schema is
  `LoginKeyInfoTable(user_name_md5, key_md5, key_info_md5, key_info_data)`.
- `user_name_md5` is `md5(canonical wxid)` — but the table stores **only the hash**, so it
  cannot enumerate accounts; it can only confirm a candidate.
- Measured on real data: `md5('wxid_gsnpwh6vh2z012')` = `5664eda7efc0c2726796446ec2662172`,
  which is exactly the value in the table, while the on-disk directory name
  (`wxid_gsnpwh6vh2z012_64b5`) hashes to something different.
- **Therefore the directory name alone yields the canonical wxid** — no SQLite parsing needed.
  `weChatLoginOracle.ts` reads `all_users/login/*` (and the `<root>/login/*` variant), strips
  the `_<4 hex>` suffix, and uses the list to separate real accounts from leftover directories.
  `keyInfoDbHasAccount()` is kept as an independent md5 cross-check for if WeChat changes its
  directory naming.

## Why this is bounded rather than exhaustive

`chatService.ts` (507 KB), `ExportContext.ts` (324 KB), `appMain.ts` (256 KB) and `wcdbCore.ts`
(224 KB) cannot be exhaustively audited in a finite pass with any confidence. Rather than
produce a large, plausible-looking list of speculative findings, this sweep targeted the
categories that have actually produced shipped bugs in this repository's history —
platform gates, swallowed errors on the connect path, and explicit markers — and reports the
rest as unverified.

## Found during the v1.0 UI pass (2026-09-13)

- **WeportAI could open onto an empty conversation.** `WeportAiPanel.openChat()` guards its
  async `ai:getChat` reply with `activeIdRef.current !== id`, but that ref was only written by
  a `useEffect`. React schedules a state update as a macrotask, so a fast IPC reply can land
  first, the guard treats the response as stale, and `messages` never gets set — the panel
  stays on the empty hero for good. Fixed by writing the ref synchronously next to
  `setActiveId(id)`.
  - Found by the screenshot harness, not by review: the demo conversation *was* requested
    (`[ai-trace] ai:getChat <- ["demo-chat-1"]`) and returned, but nothing rendered, so
    `ai.png` silently stopped being produced. The harness had been treating that as
    non-fatal, which is exactly how this stayed invisible.
  - A trace hook (`WEPORT_TRACE_AI=1` → `[ai-trace] <channel> <- <args>`) was added to
    `installScreenshotDemoHandlers` to make the next occurrence of this class of bug
    diagnosable instead of guessable.
- **The `WEPORT_V09_DUMP` responsive probe never ran in the gate that matters.** It lives in
  `runV09DumpMode`, which fails at its own group-analytics step, so the per-page layout
  assertions were dead code. The WeBot assertions now live in the screenshot harness's
  responsive pass, which does run.
- **`capture-ui.ps1` had a 120s budget left over from the 12-capture era.** With 17+ captures
  the app was being killed mid-run (during the WeportAI step), which looks like a capture
  failure but is a budget failure. Now `-TimeoutSeconds` (default 300).

## Found during the round-16 UI pass (2026-09-13, later)

- **`--accent` was a `color-mix()`, and Chromium does not support nested `color-mix()`.**
  In dark mode `--accent` was `var(--accent-raw)` (a literal), so everything worked; in light
  mode it was `color-mix(in srgb, var(--accent-raw) 72%, #000000)`, and every one of the ~27
  declarations of the form `color-mix(in srgb, var(--accent) N%, …)` — primary buttons, card
  borders, active-state fills — became invalid at computed-value time. The buttons lost their
  background entirely, which put white text on a white panel: **contrast ratio 1.00**.
  - Found by the light-mode contrast audit (added last round), which is the only reason this
    was visible: the dark-mode screenshots looked fine because the fallback for a transparent
    button is a dark panel.
  - Fixed by making `--accent` a **literal colour in every mode** (six darkened values in
    `theme.scss` for the presets; `appearance.ts` computes the same 0.72 factor for custom
    accents) and by giving `.primary-btn` a real `background-color` next to its gradient —
    the audit reads `background-color`, so a gradient-only button would have been reported as
    transparent even when it rendered correctly.
- **Every `font-weight: 600+` in the app was Chromium's synthetic bold.** The bundled font
  (仓耳渔阳体 W03) has one Regular face, no `GSUB`/`GPOS`, and `fsSelection` = REGULAR. At small
  CJK sizes the synthesised bold smears the strokes; side-by-side crops of the 朋友圈 statistics
  row show it clearly. `font-synthesis-weight: none` now lets the real outlines through.
- **`font-variant-numeric: tabular-nums` made digits switch typeface.** The font has no `tnum`
  feature, so the request sent Chromium looking for a face that does, and numbers rendered in a
  different family from the surrounding text. The 27 declarations were removed.
- **34 emoji assets were reported missing by a bad diff, not by the build.** `dist/assets/face`
  is only one of five emoji subdirectories (`gesture`, `blessing`, `animal`, `other`); comparing
  against a flattened list made it look like a packaging bug. Re-checked per relative path:
  109/109 present. Recorded because the false positive was convincing.
