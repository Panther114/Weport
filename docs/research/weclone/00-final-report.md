# WeClone 全面批判性分析（研究 + 实测 + 架构建议）

> 状态：**分析完成，未实现任何新架构**。本文档是研究结论与建议，不含新功能的落地代码。
> 唯一的代码改动是为了**跑通现有管道**而做的一处最小修复（见 §2.3），它不影响任何架构决策。
>
> 日期：2026-09-19 ｜ 语料：本机真实微信数据（184 个会话 / 10.4 万条消息 / 2026-03-26 → 2026-09-13）

---

## 0. 一页结论

四句话：

1. **克隆"不像本人"不是调参问题，是架构问题，而且有可引用的实证。** 用"描述风格的文字"去驱动模仿，在论文里的实测准确率**低于 7%**；换成"给几段本人原话让它接着写"，同一批模型达到 **99.9%**。我们现在的 25000 字人格档案 + 14 条检索原话，正好站在弱的那一侧。
2. **真正被喂给模型的"本人语气证据"只有约 1%。** 一轮对话的上下文里，模型写的*关于他*的散文约 25000 字，他的*原话*最多 14 条、约 260 字。语料里那 22.4 MB 的语气证据，99% 从来没有出现在生成现场。
3. **那份档案本身是"第三代压缩"。** map 阶段只让模型看到语料的约 27%，reduce 又把它压到 ≤5 万字，五份 MD 再各自从这 5 万字里"重写"一遍 —— 于是 MD 里的语气信息来自原始语料的约 1.5%，而且是模型转述过的。
4. **而且要命的是：现在的管道跑不完。** 两次复现都在 reduce 阶段失败（`归并结果为空，请重试`），磁盘上只会留下语料、没有档案。用户最后一次生成就是这么死在半路的。原因是一个**静默的空回复**：流被截断时 adapter 返回 `content: ''` 且不抛错，重试逻辑因此一次都不会触发（已定位并最小修复，见 §2）。

### 0.1 重要修正（实测跑完之后）

我原本的假设是"档案产得不行，所以要多花 token 重做生成管线"。**实测推翻了这个假设。**

真正跑完一次（38 片 / 71 分钟 / 输入 48.5 万 token / 输出 31.5 万 token）之后，产出的档案是**好的**：

- `profile.md`（22,801 字）里有一节 **「多面性：同一件事在不同人面前完全不同的说法」**，按**七种对象**分档（对老师 / 对同龄技术伙伴 / 对游戏群 / 对私聊好友 / 对家人 / 对 filehelper / 对陌生人），**每一档都带原话与日期**；还有语域随时间的迁移、错字族、`gay` 的十一种用法、`滚木`/`牢大`/`诗人`/`坠机` 这类黑话、以及一节**「证据薄弱 / 不要编的部分」**。
- 关键的是，它**连"怎么连发""怎么用 `*` 更正错字"都写出来了**：`打错字后用 * 星号重发纠正`、`一条一发，或把一句话拆成多条连发`。
- `language.md`（6,821 字）是一份**按语用功能分组、带日期的逐字原话库**（日常寒暄/吐槽/兴奋/工作沟通/玩梗/关心别人/生气），正是研究里说的"show, don't tell"素材。

**所以瓶颈不在生成，而在聊天时的拼装。**（详细证据见 §4.2–§4.4。）

## 2. 先说阻断性问题：现在的 v1.0.1 **生成不出一份完整克隆**

### 2.1 事实（三次运行，两次失败，一次被打断）

| # | 方式 | 结果 |
|---|---|---|
| 1 | `verify-v101.mjs`（安装版 + 真实数据） | 扫完 184 个会话、跑完 map，**停在 `profile.md` 之前**；随后窗口被"闲置回收"销毁、探针抛 `Target page has been closed` |
| 2 | GUI 触发（磁盘轮询） | 扫完 → map 37 片 → **layer-1 归并 2 组全部返回空** → 退回上一层 → 最终归并也返回空 → `生成失败：归并结果为空，请重试` |
| 3 | 打补丁后的 dev 构建 | **跑通**（见 §2.4） |

第 2 次运行留下的盘面：`weclone-staging/wxid_gsnpwh6vh2z012/` **只有语料，没有 `metadata.json`、没有五份 MD**。这与用户机器上"克隆目录只剩 `chunks.jsonl` + `voice.jsonl`"的状态完全一致 —— **用户上一次生成也是这么失败的**。

### 2.2 根因（已定位到行）

`weCloneService.callLlm()`（第 1264 行）：

```ts
const result = await getProviderAdapter(profile).stream({ … })
return String(result.content || '')        // ← 空内容被当成"成功"
```

而 `providerAdapters.ts` 的 OpenAI 兼容 adapter（第 256 行）**只在 `delta.content` 上累加**：

```ts
const text = typeof delta.content === 'string' ? delta.content : ''
if (text) { result.content += text; input.onText(text) }
```

于是当 SSE 流被中途切断（本机实测频繁出现 `fetch failed` / `ERR_CONNECTION_TIMED_OUT`）时，`content` 为空、`finishReason` 为空，**既不抛错也不重试**。

`callLlmWithFallback()` 的重试条件只看异常（第 1353 行 `if (!isProviderUnavailable(lastError)) throw e`），所以：

- map 阶段：空回复 → `if (!cleaned) throw new Error('空摘要')` → 该片退回"本地统计兜底"（内容等于没有）；
- reduce 阶段：空回复 → `throw new Error('归并结果为空')` → 该组作废；**两层都空之后，整次生成失败**。

日志证据（补丁后暴露出来的真相）：
```
[WeClone]（分片 13/37） deepseek-v4.1-flash 瞬时失败（空回复（finish_reason=none）），4000ms 后重试第 2 次
[WeClone]（分片 18/37） … 8000ms 后重试第 3 次
```
`finish_reason=none` = **流没有正常结束**，不是"输出超长被截断"。

### 2.3 最小修复（已应用，未提交）

`electron/services/weCloneService.ts`，两处：

```diff
       reasoningEffort: this.resolveReasoningEffort(),
+      // 与 WeportAI 主链路一致：带上这个模型声明的输出上限
+      maxOutputTokens: profile.modelMaxOutputTokens,
       signal: signal ?? AbortSignal.timeout(LLM_CALL_TIMEOUT_MS),
@@
-    return String(result.content || '')
+    const content = String(result.content || '')
+    if (!content.trim()) {
+      throw new Error(`空回复（finish_reason=${result.finishReason || 'none'}）`)
+    }
+    return content
@@
-          if (!isProviderUnavailable(lastError)) throw e
-          const isTransient = isTransientNetworkError(lastError)
+          const isEmptyReply = /^空回复/.test(lastError)
+          if (!isProviderUnavailable(lastError) && !isEmptyReply) throw e
+          const isTransient = isTransientNetworkError(lastError) || isEmptyReply
```

`npx tsc -p tsconfig.node.json --noEmit` 通过。这是**让现有功能能用**的修复，不是新架构的一部分；用户可以直接留下或回退。

### 2.4 附带发现（不是本次要解决的问题，但值得记下）

- **窗口"闲置回收"会打断长任务**：`verify-v101.mjs` 把 `WEPORT_DISCARD_DELAY_MS` 固定成 10 分钟，而生成要 20 分钟以上 —— 探针必然在半路被销毁窗口。探针应改成"完成后才关应用"或把回收推迟到小时级。
- **CLI 引擎模式在本机跑不动**：`Weport.exe --cli` 报 `provider 配置已加密但当前进程无法解密（拿不到系统密钥存储）` + 三次注册表读取失败，随后进程以 `-1` 退出。也就是说 `weclone.generate` 的 CLI/TUI 路径在这台机器上目前不可用。
- **磁盘上有一个残留目录** `weclone-staging/__probe_delete_me__`（`id: wc_probe_delete`，`messageCount: 1000`）。它会被任何"扫描 staging 目录找克隆"的脚本误判成真克隆（我的第一版轮询就中招了，还因此把正在跑的生成掐死）。
- **`weCloneService.ts` 在本次分析前后被改动过**（11:24），12:04–12:06 有一次 v1.0.1 重新构建 + 重装（安装版 `app.asar` 时间戳 12:05:54）。安装动作会杀掉正在运行的实例 —— 这也是第 1 次运行中途死掉的原因。

## 4. 克隆在生成现场**实际拿到**的是什么：约 1% 的语气证据

一轮对话的上下文由这些部分组成（常量来自 `weCloneService.ts`）：

| 成分 | 预算 | 内容性质 |
|---|---|---|
| `profile.md` + `relationships.md` + `knowledge.md` + `timeline.md` | 实测 **≈24,700 字符** | **模型写的、关于你的中文散文** |
| 风格指纹块（`fingerprint.txt`） | 几行统计描述 | 模型读到的**数字**（不是你说话的方式） |
| 检索到的历史片段 | 24 条 / 14,000 字符 | 含对方的话；**按当前这条消息的关键词**检索 |
| 语气样本（`voice.jsonl`） | **最多 14 条 / 4000 字符** | 唯一的"本人原话"来源 —— 14 × 中位 14 字 ≈ **200 字符** |
| `language.md` | — | **v1.0.1 起被刻意排除在 system prompt 之外** |

> **约 25,000 字符的描述，对比 14 条原话（约 200–330 字符）。"你真正怎么说话"在生成现场占约 1%。**
> 而且那 14 条是按**话题关键词**检索出来的：对方说"hi"/"在吗"时几乎检索不到，退化成"最近说过的话"；对方提到 `djh` 时因为查询只有 3 个字母、分词后无信息量，**一条都检索不到**（这正是克隆回答"idk who djh is"的机制）。

### 4.1 档案本身是"第三代压缩"（精确数字）

```
语料正文                     19,643,654 字符  = 100%
map：37 片 × 每片 24,000 字   888,000 字符    =  4.5%      ← 模型真正"看到"的
reduce：压到 ≤50,000 字符      50,000 字符    =  0.25%     ← 五份 MD 的**唯一**输入
五份 MD（32–57 KB）              —            ← 从那 0.25% 再经模型转述一遍
```

两个必须指出的细节：

- **分片数本身算错了。** `generateClone` 里是 `const totalChars = stats.messageCount * 32`（"平均每条 32 字符"），于是 104,017 条 → 3.33M 字符 → 37 片。**真实正文是 19.64M 字符，差了 5.9 倍** —— 也就是说，即使不管 `buildShardContext` 的 24k 上限，分片数也是按一个错误的语料规模定的。
- **`buildShardContext` 又把每片砍到 24k。** 19.64M ÷ 38 = 每片 517k 字符，实际只喂 24k（4.6%）。两道采样叠起来，效果是"每一段时间都只被读了很小一部分"。

```
本人原话（语气样本）        ≤14 条 ≈ 200–330 字符
                          ─────────────────────────
"你真正怎么说话"的占比：约 0.5%（不是 1%，因为这一版档案更大）
```

### 4.3 三个已被产物证实的、聊天侧的具体缺陷

**① 最好的语气素材被生成出来、然后被扔掉了。**
`language.md` 是一份**按功能分组、带日期**的逐字原话库（寒暄/吐槽/兴奋/工作沟通/玩梗/关心别人/生气），例如：

> 吐槽：`我他妈考的和那个richard Z一个分`（2026-04-27）、`bro my fucking clipboard`（2026-08-15~20）、`绷不住了`（2026-09-14~19）
> 玩梗：`Gay Claude`、`ok Glaude, Deepsea, Stellyra 3选1`、`Executive led comp = gay`、`sehr gut`、`吓哭了`
> 自我修正：`its a community plugn` → 下一条 `plugin`；`journel` → `*nal`

`chatWithClone` 组装 prompt 时**只传了 profile / relationships / knowledge / timeline 四份**（`weCloneService.ts` 的 `mds:` 字段，带注释"language.md 不进 system prompt"）。也就是说：**管道花了 6,821 字把"你按功能怎么说话"整理好，然后在生成现场一条都不用** —— 只留下最多 14 条按**话题关键词**检索的样本，而 `hi`/`在吗`/`djh` 这类查询恰好检索不到。

**② `timeline.md` 里没有时间线。**
406 字，内容是**把指纹统计原样抄了一遍**（`语言特征（对齐用，全部来自统计口径）`），没有任何日期—事件。模型被要求写"按年份→月份的大事记，2000–6000 字"，结果交了一份统计表。后果：克隆**没有时间轴**，"什么时候发生的事"这类问题只能靠检索碰运气或编。

**③ 逐字命中率 2.2%。**
24,540 条 ≥6 字的本人原话里，只有 **544 条**以逐字形式出现在五份档案中。也就是说档案里的语气证据是**零散的引文**，不是可模仿的分布。

### 4.4 确定性指纹那一块本身也需要修

`fingerprint.txt`（唯一"算出来的、可复现"的部分）目前混着噪声：

- **脱敏占位符进了"口癖"**：`已脱敏:住`、`脱敏:住址`、`敏:住址证`、`住址证件]`、`已脱敏:密`、`脱敏:密码`；
- **微信表情的"名字"被当成 n-gram**：`破涕为笑]`、`涕为笑][`、`为笑][破`、`笑][破涕`、`流泪][流`、`泪][流泪`；
- **系统提示进了口癖**：`违规昵称f`、`规昵称f0Y`；
- **标记表被单个字母占满**：`u 30.7 次/百条`、`k 20.5 次/百条`（`k` 来自 MARKERS 里的 `'k'`，任何含字母 k 的消息都计数）；
- **表情比例被低估**：报"1%"，但 `[Sob]` 单独就出现 463 次、`[ThumbsUp]` 46 次、`[Panic]` 91 次 —— 它们**不在** `MEDIA_TAG_RE`/`EMOJI_RE` 的匹配范围内，所以统计不到；
- **污染还漏进了成品档案**：`profile.md` 第 362 行的"高频中文片段"里直接写着 `脱敏:[已脱敏:住址证件]]`。

同时，"英文词与搭配"这一栏其实**抓得很好**（`sob sob`、`sehr gut`、`max shuang`、`panic panic`、`helmut kohl`、`friedrich von honhenzollern`、`gay`、`tmr`、`gchat`、`grok`）—— 说明"算出来的"这条路是对的，只是**清洗与显著性**没做。

### 4.5 一个副作用：`profile.md` 第 10 节会诱发"背台词"

`## 10. 扮演速查卡（可直接照抄的句式）` 给了 `ok` / `okok` / `ye` / `nah` / `6` / `nje` / `sehr gut` 这类**可照抄**的短语表。用户此前明确反对 system prompt 里出现"预设的行为引文"（旧版拒答节的 `例如："这个我不想聊"` 就是因为会被复读而删掉的）。现在这条以"速查卡"的形式回来了，而且**在 always-on 的档案里** —— 这正是会产出"每句都塞同一个口头禅"的机制。

## 5. 为什么"描述"在原理上替代不了"原话"（有实证，不是我猜的）

### 5.1 最直接的一篇：同一个任务、同一类模型、只换提示策略

Jemama & Kumar, *How Well Do LLMs Imitate Human Writing Style?*（IEEE UEMCON 2025, [arXiv:2509.24930](https://arxiv.org/abs/2509.24930)）用一套免训练的作者验证器（TF-IDF 字符 n-gram + 句向量，域内 97.5%、跨域 94.5% 准确率），对五个模型 × 四种提示策略做对照：

| 提示策略 | 风格模仿效果 |
|---|---|
| **zero-shot + 统计风格摘要**（＝我们现在这套） | **准确率 < 7%**，而验证器还"以 >95% 的置信度"给出错误判断 —— 作者原话：**"the statistical style summaries provided in prompts were not effective anchors for imitation"** |
| one-shot（给一段真实样本） | 67.6% – 94.7% |
| few-shot | 最高是 zero-shot 的 **23.5 倍** |
| **text completion（给真实前文让它接着写）** | **≥99.9%** 与原作者一致 |

同一篇还有一个对我们很重要的第二结论：**"像"和"不露馅"是两件事** —— 即使作者一致性 99.9%，模仿文本的困惑度平均只有 **15.2**，而真人文章是 **29.5**。克隆可以骗过作者验证，但仍然"太顺滑"。

### 5.2 最贴近我们场景的一篇：非正式文体是最难的

Wang et al., *Catch Me If You Can? Not Yet*（Findings of EMNLP 2025, [ACL](https://aclanthology.org/2025.findings-emnlp.532/) / [arXiv:2509.14543](https://arxiv.org/html/2509.14543v1)）：>400 位真实作者、四类文体、每模型 >4 万次生成。结论是模型能模仿新闻/邮件等**结构化**文体，但**"struggle with nuanced, informal writing in blogs and forums"**，而且生成物"often default to an average, generic tone and remain readily detectable as AI-written"（被判为真人写的比例**始终低于 55%，常常低于 20%**）。

微信聊天是非正式轴的**最末端**。另一份经典证据（Abbasi & Chen 2008, Writeprints）：四个语料里 **chat 是最弱的一类**（25/50/100 个作者时只有 50.4% / 42.6% / 31.7%，而 email 与 eBay 评论是 92–96%）。

### 5.3 生产侧的做法和我们的直觉正好相反

- **SillyTavern（向量化聊天）**：摘要是用来**建检索键**的，真正塞进上下文的是**原文** —— *"The summarized message does **not** replace the original message in chat. If a vector search matches the vector of a summarized message, **the original message is retrieved** from chat history and shuffled into context."* 我们现在做的**恰恰相反**：把压缩结果当成了注入内容。
- **Character.AI** 官方建议人设 **90–150 词**，并提示更长的会被**降权**；社区惯例是 *"specific, consistent, and lean"*、*"Example messages are the most direct way to fix a voice"*。我们发的是 **25,000 字符**。
- **ChatHaruhi**（[arXiv:2308.09597](https://arxiv.org/abs/2308.09597)）用纯 prompt 人设做了实验，直接点名了我们的症状：*"the chatbot's conversational style is still heavily influenced by the underlying language model."*
- 社区的俗称叫 **"Standard Persona Syndrome"**：*"long conversations drift back toward the base model's voice … The persona is still in the system prompt — the model just gives it less weight as turns accumulate."*
- **人格漂移有测量**：LLaMA2-chat-70B 在 **8 轮内**就出现显著漂移（注意力随轮次衰减）。缓解手段是**在生成位置附近重复注入** —— 而不是把材料堆在最前面。

### 5.4 检索本身是对的，但要检索"情境"而不是"关键词"

LaMP（personalisation 基准，[ACL 2024](https://aclanthology.org/2024.acl-long.399.pdf)）报告检索增强的个人化带来 **+12.2%（zero-shot）/ +23.5%（fine-tune）** 的相对提升；而系统对比里 **RAG 个人化 +14.92% vs PEFT +1.07%**（[lamp-benchmark](https://github.com/lamp-benchmark/lamp)）—— 也就是说，**在我们这个"一台笔记本 + 一个托管 API"的约束下，检索路线是对的、且性价比最高**。

问题不在"用了检索"，而在**检索的键和单位是错的**：
- 键是"话题关键词"（BM25 对 `hi` / `在吗` / `djh` 这类查询无能为力），而不是**情境/语用功能**（打招呼该配打招呼）；
- 单位是 ~800 字符的混装分块（“1 个分块里可能一半是别人在说话”），而不是**一对往返（exchange）**；
- **没有任何"对谁说"的维度** —— 184 个会话就是 184 个语域，现在被压成了一个声音。

## 7. 建议架构：**语料是唯一真相，摘要只做路由，原话进现场**

### 7.1 一句话原则

> **能被算出来的不要问模型；要模仿的必须是原文；摘要只能用来"找"，不能用来"读"。**

这条原则同时解决 §5 的三个实证结论（描述无效、非正式文体最难、摘要不可逆丢信息）。

### 7.2 分层设计

```
L0 语料层（逐字、可寻址、留痕）
   msg     一条微信消息           ← 只作为溯源目标，永不单独检索
   exchange 一组"对方说 → 你说"     ← 【语气样本的基本单位】= 教"你怎么回"
   segment  话题连贯的一段（15–40 条）← 【记忆检索的基本单位】
   session  一个会话/群            ← 只做导航
   partner  会话对象 → 语域档案

L1 声音层（本地统计，确定性、可复现）
   全局指纹 + 分语域指纹（按会话/语域簇）+ 分时期指纹（近 30/90 天 = "现在的你"）
   维度：长度分布 · 连发分布 · 标点密度 · 大小写 · 占位符表情 · 词内混写 ·
        `*` 更正率 · 错别字对 · 显著高频片段（log-odds + Dirichlet 先验 + bootstrap）·
        从未用过的词（反向约束）
   用途：(a) 生成时的约束  (b) 生成后的打分校准  —— 不只是"写进 prompt 的一段话"

L2 记忆层（事实，可检索、有出处）
   保留原文段落可检索；派生摘要**只做检索键**，不直接作为注入内容
   混合检索（BM25 + 可选本地向量）→ 命中 segment 后**展开成 exchange**
   矛盾不合并：两条都留、各带时间（人是会变的）

L3 情境层（生成现场，真正的修复点）
   ① 查询构造：当前消息 + 最近 N 轮 + "对谁说" → 而不是只拿这条消息的关键词
   ② 语用功能路由：打招呼/提问/玩梗/办事/吐槽/纯表情 → 同功能检索
   ③ 取 exchange（对方 + 你），按"功能 × 语域 × 话题相近但文本不重复"挑选
   ④ 注入形态：**一段可续写的真实对话**（带日期、Them/Me 标签）→ 当前这条 → 生成
      （这就是 ≥99.9% 的那个机制；且放在**紧邻生成位置**，对漂移最有效）
   ⑤ 连发：按真实 burst 分布决定发几条、如何切分；`*` 更正可作为"第二条消息"显式模拟
   ⑥ 生成后确定性后处理：长度带、标点、大小写、助手腔禁用词、占位符表情替换

L4 提示层（缓存友好）
   [稳定前缀] 短核心规则 + 当前语域档案 + 硬约束   ≈ 600–1500 字符（不是 25k）
   [易变块]   检索到的记忆 + 语气样本 + 本轮消息
   稳定前缀顺序固定、绝不按分数重排；把"顺序会变的东西"放到前缀之后

L5 验证层（先建它，否则任何改动都无法判定）
   held-out 下一句预测（时间切分，防泄漏）· 四臂对照 REAL/CLONE/BASE/PARROT
   单条可用指标：per-author BPC（唯一在 1–30 字尺度上有功效的指标）
   头条指标：Recovery@1（在 20 条真人消息里排出真正的那一句；随机 5%）
   硬门：抄写率 ≤2% · canary 零泄漏 · 高于随机 p<0.05 · 单项不超噪声底 2×
   成本：30 例烟测 ≈ $0.01–0.06；200 例 × 4 臂 × 3 采样 ≈ $5（含缓存 ≈ $0.55）

L6 反馈层
   每条回复给"像/不像"；生成 3 个候选让用户挑一个（偏好数据比"像不像我"信息量大得多）
```

### 7.3 明确的**删除清单**

| 删除 | 理由 |
|---|---|
| 把 25k 字散文当 always-on 人格通道 | §5.1/§5.3：那是被实证证明最弱的通道；且 25k 字符本身让模型降权 |
| `language.md` 排除在 prompt 之外 | v1.0.1 的这条改动方向对但剂量错：应该**增加**情境化逐字证据 |
| 按话题关键词检索"语气" | `hi`/`在吗`/`djh` 这类查询先天检索不到；应改为"功能 × 语域"检索 |
| 单条消息 = 一次回复的假设 | 与真实连发分布不符，是结构性可见的破绽 |
| 180k 字符的 prompt 预算野心 | 目标不是"能塞多少"，而是"这一轮最少的高信号 token" |
| 分数排序的注入顺序 | 破坏前缀缓存，也让风格证据远离生成位置 |

### 7.4 落地优先级（按"证据强度 ÷ 工作量"排序）

| 优先级 | 动作 | 依据 | 工作量 |
|---|---|---|---|

| **T2** | 检索改为"语用功能 × 受众"（现成材料：184 个会话 + `language.md` 的功能分组） | §4.3 的 `djh`/`hi` 失败模式 | M |

## 8. 评测：必须先建，否则上面每一条都无法判定

现在**没有任何评测** —— 改动的效果只能靠"感觉像不像"。调研给出的可落地方案（详见 `05-evaluation.md`）：

- **主基准**：held-out 下一句预测。从时间上切出后 20% 的真实对话，喂前文，让克隆预测本人**真实发过的那一句**。四臂对照：`REAL`（本人真实消息，天花板）/ `CLONE` / `BASE`（裸模型）/ `PARROT`（直接抄检索结果）。
- **唯一在 1–30 字尺度上有功效的自动化指标**：**per-author BPC**（按 token 平均的交叉熵，而不是按消息平均）—— 12 字的一条消息能贡献 ~7 个观测，其它指标只有 1 个。
- **头条单值**：`Recovery@1` —— 把真实那一句混进 20 条真人消息里，看克隆的输出能把它排到第几（随机 5%）。它不能靠抄写取胜（候选池全是真人真话），跨版本可比。
- **硬门**：抄写率 ≤2% · canary 零泄漏 · 高于随机 p<0.05 · 单项不超噪声底 2×。
- **防自欺**：指纹里已经用到的统计量（长度/标点/表情）**不能同时当打分指标**，否则测的是"听不听话"；需要一个"只给指纹"的对照臂。
- **人评的真实功效**：30 次强制选择只有 **51%** 的检验功效能发现 65% 的真实差异；要在 80% 功效下检出 65% 需要 **69 次**。所以别用一个 30 次的盲测下结论。
- **成本不是问题**：30 例烟测 ≈ $0.01–0.06；200 例 × 4 臂 × 3 采样 ≈ **$5**（前缀缓存命中时 ≈ $0.55，已按 models.dev 的真实价格核算）。
