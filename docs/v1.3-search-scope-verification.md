# V1.3 search, account scope and storage verification

> Historical foundation receipt from before the feature implementation. See [current implementation status](v1.3-implementation-status.md) for later changes and remaining acceptance.

Verified on Windows x64, Node v24.19.0, 2026-10-20. These are current implementation receipts, not acceptance of the future V1.3 search architecture. All added fixtures are generated, use private temporary directories, and open no Electron windows or source WeChat databases. No second real account or native macOS/Linux run was available.

## Reproduce

```powershell
npx vitest run electron/services/searchIndexService.test.ts electron/services/annotationsService.test.ts electron/services/mcpService.test.ts electron/services/imageKeyAccountScope.test.ts
node --expose-gc scripts/verify-v13-search.mjs --million
```

The script bundles the production pure services into a temporary directory, checks 16 fixture invariants, runs 100k and 1m generated-message workloads in separate Node processes, removes its temporary data, and saves `.ui-probe/v13-search-receipt.json`. The receipt contains generated text and measurements only. It accepts `--million` explicitly to include the larger workload; without it only 100k is measured.

## Current architecture and demonstrated correction

`searchIndexService.ts` persists gzip JSON shards in account directories, with an atomic manifest commit and generation-based garbage collection. Search loads documents into memory and performs lowercase substring matching with multi-term AND and a bounded top-candidate heap. It is an O(document count) scan. There is no FTS5, semantic/vector retrieval, embedding index, OCR retrieval, or SQL full-text query in this service.

Defaults include 1,000,000 documents, 2,000 characters per document, a nominal 96 MiB text limit, 2.5 s query budget, 2,000 maximum retained candidates, and a 200,000 matching-document scan guard. The actual text-limit accounting uses JavaScript string lengths; it should not be interpreted as a measured resident-memory limit. Initial ASCII queries additionally build a lowercase copy. Query totals are counts in the scanned portion; `truncated` also covers candidate retention, so it can be true even when the scan counted all matches.

A reproducible bug was corrected: the deadline was checked only after matching documents. Queries with no matches or excluded scopes could bypass that check. The regression uses a deterministic advancing clock and failed before the change (`truncated` was false). The scan now checks time every 1,024 visited documents before filters. This bounds the scan approximately; initial corpus loading and the first lowercase-copy allocation are still outside this periodic scan check, and individual synchronous operations do not yield to the event loop.

## Correctness and isolation

The existing four targeted files passed 98 tests before the change. The final combined run passed all 101 tests across four files in 10.94 seconds, including the new scan regression and two additional MCP authentication cases.

Generated fixtures passed mixed Chinese/English/case-insensitive AND matching; exact local ID plus database/table provenance; inclusive date endpoints in milliseconds and legacy seconds; sender/session/type filters; excluded sessions; account A → empty account B → account A reloading; recent in-place edits; newly appended rows; and copied-index/copy-annotation loading from alternate roots. Existing tests also cover exact server IDs beyond JavaScript's safe integer range, repeated local IDs across tables, pagination/cursor invalidation, account switching during asynchronous reads/builds, damaged shards, manifest corruption, canceled generation commits, and legacy annotation ownership.

Incremental indexing intentionally reparses only the latest 20 row-ID positions per table. An edit before that window and a deleted individual row remain stale after an incremental build; both were reproduced. A forced rebuild corrected both. New high-ID rows backfill incrementally, but arbitrary low-ID historical inserts are not guaranteed by that cursor/window design. The fixture checks these limitations explicitly instead of claiming full change-data capture.

Search corpus directories are account-scoped. Annotation files use hashed account identities, preserve separate cached states, and give legacy unscoped data to only one account. Existing tests verify a malformed legacy owner marker cannot let another account claim it. Image-key account selection has 15 passing generated-template tests. These are simulated account-boundary tests; they do not establish behavior with two real logged-in accounts.

## Measured generated-data baseline

Both workloads used short generated messages (about 30 characters), one database/table and batches of 5,000. Five sequential queries per case were measured after building in the same process. These numbers include JavaScript service work, not native DB extraction, renderer responsiveness or IPC. Builds ran on a shared machine and are observations rather than regression thresholds.

The final receipt was generated at 2026-10-20T09:12:35.542Z. At 100k, Chinese/English/mixed sparse queries each counted exactly 100 matches. At 1m they counted 1,003. Mixed-query ranges were 2.07–2.33 ms and 25.42–26.44 ms respectively; absent-query ranges were 1.61–6.31 ms and 24.30–25.61 ms. These short strings and small source-table count do not establish performance for long messages, many native shards, cold persisted-index loading, or a real 1m-message profile. Memory is the worker's RSS after build and explicit GC, not a sampled peak or whole-app memory.

## MCP and AI/storage boundaries: implemented versus future

`mcpService.ts` binds to loopback by default, uses one bearer token, rejects a foreign browser Origin and tracks HTTP transport sessions. Nine HTTP tests pass, including absent/wrong bearer → 401, foreign Origin → 403, stale session → 404, and valid initialization/termination. Its optional search `sessionId` is a caller-supplied query filter. There is no per-client session allowlist, capability token, account lease or permission-scope enforcement in that service. MCP transport session IDs must not be described as data scopes. Tools use the currently connected chat services; the future explicit MCP scope design is not implemented or verified here.

Source inspection of `weportAiService.ts` shows chat history under `<userData>/weport-ai/sessions` and an index under `<userData>/weport-ai/index.json`. Workspace selection is configured `weportAiWorkspaceRoot`, then `<exportPath>/WeportAI`, then `<userData>/WeportAI`; chat notes are below `chats/<chatId>` and long-term memory below `memory`. Neither root includes the selected WeChat account. AI history and memory are currently shared application workspaces, not account-isolated storage. No account-isolation claim is made for them.

Changing `workspaceRoot` currently updates configuration; it does not copy or migrate earlier workspace files. The generated tests demonstrate that already-copied search/annotation data can load under alternate constructor roots. They do not prove an in-app storage relocation wizard, transactional relocation, free-space checks, migration rollback, or AI workspace migration. Those future storage-management requirements remain unimplemented/unverified. This module made no writes to the real profile and no real-message query output is retained.
