## 2. Workstream A — Bug fixes and macOS compatibility

### 2.1 A1 · macOS packaging & signing (issue #18) — **highest priority**
**Root cause (verified via git):** `git show HEAD:package.json` contains `hardenedRuntime: false` and `gatekeeperAssess: false` but **no `identity` key**. `release.yml` sets `CSC_IDENTITY_AUTO_DISCOVERY: 'false'`. With no identity and discovery off, electron-builder warns "skipped macOS application code signing" and continues — the `.app` keeps only *linker* ad-hoc signatures on the inner binaries, so `codesign --verify --deep --strict` reports `errSecCSResourcesMissing` ("code has no resources but signature indicates they must be present") and Finder says **"已损坏"**.

**Important distinction to communicate to users:** there are two different "damaged" failures. (a) *Policy* rejection — properly signed, not notarized → clearable with right-click-Open or `xattr -cr`. (b) *Invalid seal* — this bug → **no** bypass works. v0.9.11's mac build hit (b).

**Implementation:**
1. Commit the in-tree `"identity": "-"` (electron-builder 26.15.3 genuinely ad-hoc signs when `identity === '-'`, producing a real `Contents/_CodeSignature/CodeResources`).
2. Harden `scripts/verify-mac-pack.sh` check 6: it currently greps `codesign -dvv` for `Signature=adhoc`, which **also passes on a silently-skipped build** (linker signatures print the same string). Replace with an assertion on `Format=bundle with Mach-O` + `Sealed Resources version=2 … files=N`, and/or `test -f Contents/_CodeSignature/CodeResources`.
3. Add the same gate to `.github/workflows/mac-attach-release.yml` (it backfills mac installers onto existing releases and currently bypasses the gate).
4. Document that `unzip`/`ditto` do **not** propagate `com.apple.quarantine` while Finder's Archive Utility does — so the CI round-trip test can never observe Gatekeeper; ship the one-line recovery (`xattr -cr /Applications/Weport.app`) in the release notes and in-app.
5. **Remove `com.apple.security.get-task-allow=true`** from `electron/entitlements.mac.plist`. Apple rejects notarization outright when it is present, and it is the wrong direction for what it looks like it is for (it makes *Weport* attachable, it does nothing to help Weport attach to WeChat — see A3). Keep `cs.debugger` for now but move it to the helper story.
6. Ship a documented "macOS troubleshooting" section covering right-click-Open vs `xattr -cr` vs the "damaged" dialog, and add a preflight that detects and explains the three cases distinctly.
7. Drop `resources/welive/macos/arm64/welive` from the mac package — it has no runtime consumer (`grep -r welive electron/` finds only a *data-import* naming), and a stray unsigned nested `WCDB.framework` under `Contents/Resources` fails `--deep --strict`.

**Acceptance:** `bash scripts/verify-mac-pack.sh release` exits 0 on the macOS CI runner; the ZIP round-trip copy also passes `--strict`; `_CodeSignature/CodeResources` exists.

### 2.2 A2 · macOS data-directory resolution — **the "Mac path is different" report**
**Verified root cause:** `electron/services/dbPathService.ts:453-471` `getDefaultPath()` iterates `~/Library/Containers/com.tencent.xinWeChat/Data/Library/Application Support/com.tencent.xinWeChat/` and returns the **first entry matching `/^\d+\.\d+b\d+\.\d+/`** — with **no account-directory validation**. On any Mac that ever ran WeChat 3.x, `2.0b4.0.9/` (the 3.x root, kept as a rollback copy) matches, so the app prefills a directory that contains no `db_storage/`, and the user later gets `-3001 未找到数据库目录`. Note `autoDetect()` at `:119-155` *is* safe because it validates via `findAccountDirs()`; only `getDefaultPath()` is unvalidated.

Also verified: the correct 4.x root is `~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/` (6+ independent first-hand sources), and `~/Documents/xwechat_files` **is missing** from the darwin candidate list even though WeFlow and CipherTalk both include it.

**Implementation:**
1. Validate every candidate before returning it, using the same `findAccountDirs()`/`isAccountDir()` predicate as `autoDetect`; return the first candidate that actually contains a `db_storage`/`session.db`, else fall back to the known-good 4.x container path.
2. Add `~/Documents/xwechat_files` to the darwin candidates.
3. Tighten `isAccountDir()` (`:294-300`) so a **3.x** account dir (`FileStorage/Image[2]`, `Message/`) can no longer be accepted on a 4.x database.
4. Prefer the account directory that actually contains `session.db`, then newest mtime, when both `wxid_X` and `wxid_X_ab12` forms exist (APFS `readdir` returns **hash order**, so "first entry" is arbitrary — this is the upstream #996 bug class).
5. Add an in-app "找不到数据库 / 路径疑似错误" diagnostic that prints each candidate path, whether it exists, whether it validated, and why it was rejected.

### 2.3 A3 · macOS key capture — a capability problem, not a bug
**Finding:** `task_for_pid()` against a modern WeChat requires the **target** to carry `get-task-allow`. Stock `/Applications/WeChat.app` is sandboxed, hardened-runtime, Developer-ID signed and notarized with `get-task-allow` **absent** — so attach fails with `KERN_FAILURE (5)` **even as root**. SIP is a *correlate*, not the cause (your `keyServiceMac.ts` comment already says exactly this, and it is right).

Compounding it: the helpers ship through `mac.extraResources`, i.e. they land in `Contents/Resources/…` — a **data** location — so `@electron/osx-sign` never signs them and they carry **no entitlements at all**.

**Implementation (do not over-promise):**
1. Keep attempting the real flow (never gate on `csrutil` alone), but **stop selling it as a normal user path.** Rewrite the mac key-status copy to state plainly: *stock WeChat on macOS 15+ cannot be attached without re-signing WeChat itself; Weport does not do that for you.*
2. Add a **preflight capability report** before the user spends 3 minutes waiting: WeChat's `codesign -dv` flags/Authority, presence of `get-task-allow`, Weport's own helper signature state (expected: *not signed at all*), `xattr -l` on the helper (a `com.apple.quarantine` xattr makes the helper never execute and produces a **misleading** "task_for_pid denied" message), SIP status, Rosetta state.
3. Make **image keys the recommended mac path** — the image-key derivation needs no attach at all (see A5).
4. Replace free-form 140-char error truncation with a closed vocabulary so support metrics aggregate (known extras today: `breakpoint_hit_but_args_invalid` from the wild is not in the list).
5. On device, verify whether ad-hoc signatures actually receive embedded entitlements on macOS 26 before relying on `cs.debugger` at all.

### 2.4 A4 · TCC / Full Disk Access
macOS 14+ gates cross-container reads even for non-sandboxed apps. Verified: the entire `electron/**` tree has **zero** references to Full Disk Access, `EPERM`/`EACCES`, or the privacy pane, and `autoDetect` swallows any failure into a generic `未能自动检测到微信数据库目录`.

**Implementation:** detect `EPERM`/`EACCES` distinctly from "not found", and surface a first-class, actionable "授予完全磁盘访问权限" panel with a button that opens the exact System Settings pane (`x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`). Add the same treatment on the manual directory picker.

### 2.5 A5 · Image keys on macOS + the regression the #15 fix introduced
**Verified:** #15 *is* fixed in v0.9.11 (`src/App.tsx:292-294` now includes `darwin`/`linux`). The mac image-key path is `kvcomm`-based and needs **no** attach/SIP: read `uin` from `…/xwechat_files/app_data/net/kvcomm/key_<uin>_*.statistic`, then `xorKey = uin & 0xFF`, `aesKey = md5(str(uin)+cleaned_wxid)[:16]`. That matches every independent implementation, and the native DAT decrypter already ships for mac.

**Regression to fix:** `src/App.tsx:929-932` now **hard-blocks export entirely** when images are selected and `imageKeysOk` is false. On a Mac where the key is unobtainable, the user is now stuck — where before they got `[图片]` placeholders. Change to a **warning with a "仍然导出" affordance**, and report the missing-key count in the result (the in-tree toast change already does this half).

**Hardening in the derivation loop:**
- Cross-check `uin` candidates against the account-directory suffix (`suffix === md5(str(uin))[:4]`) instead of accepting any positive code (naive scans produce a bogus `uin = 0`).
- Require **≥3 independent template blocks** to agree in `verifyDerivedAesKey` — a single 16-byte block with a 3-byte JPEG magic can false-positive today.
- Bound the memory-scan fallback: it is dead on WeChat ≥ 4.0.3.80 (key no longer resident; 4.1 uses PBKDF2-SHA512 × 250 000) and blocked on macOS 14.4+ by the PPL `thread_set_state` gate. Fail fast with an honest message rather than burning 60–180 s.

### 2.6 A6 · `-3999` / `-3998` — make failures legible (issue #17)
`-3999` = "open() failed, no parseable code"; `-3998` = "unhandled exception during connect". Both are client-side sentinels that are **excluded** from the security-code dialog allow-list, so the user gets a bare, meaningless string.

**Implementation:** keep the sentinels internal, but never render them alone. Attach a cause line, the searched DLL candidate list, the resolved resources path, and the WCDB `SecurityStatus` to the user-facing message, and add a **"复制诊断信息"** button wherever a code-only error appears. (The uncommitted `wcdbCore.ts` change is exactly this for the DLL-not-found branch; extend the pattern to every `-3999`/`-3998` origin.) Publish a documented error-code table in the README (`-3001`…`-3004`, `-2301`…`-2303`, `-100x`, `-2xxx`, `-3999`, `-3998`, plus the macOS helper `ATTACH_FAILED`/`SCAN_FAILED`/`HOOK_FAILED`/`FRIDA_FAILED` family).

### 2.7 A7 · WCDB host on macOS: read-only install locations
`wcdbHostClient.ts` creates a hardlink named **`WeFlow`** next to `process.execPath` (the `-1006` filename self-check); if that directory is not writable it **copies only the binary** to `{userData}/wcdb-host/WeFlow`. On macOS that copy cannot resolve `Electron Framework.framework` via `@executable_path/../Frameworks`, and no `DYLD_*` is set — so the host fails to start and the user sees a code-only error. This fires when the app is launched **from the mounted DMG or from a quarantined Downloads folder** (App Translocation ⇒ read-only mount) — a very common first-run path.

**Implementation:** on darwin, if the app directory is not writable, clone the **whole `.app` Contents** (or hardlink the framework tree alongside the binary) instead of copying one file; add a positive startup self-test in `wcdb.log` ("host exe resolved → …") so this class of failure is never silent again. **Verify on a Mac by launching from inside the DMG.**

## 4. Workstream C — Weport AI harness rework

### 4.1 C1 · Provider layer maturity
Verified current state: a **static** `providerCatalog.ts` with 80+ hard-coded model ids for `opencode-zen` and 20 for `opencode-go`; per-profile `protocol`; a `discovery` field that records models but never refreshes on its own; auth already correctly safeStorage-encrypted as one blob with masked summaries (good — keep).

**C1.1 · Make `protocol` per-model, not per-profile.** This is the biggest architectural gap. Multi-protocol gateways route by model: a single `opencode-go` profile configured `openai-compatible` serves most models and fails others (verified: `grok-4.6` on `/chat/completions` returns *"Model grok-4.6 is not supported for format oa-compat"*). models.dev already carries the mapping per model as `provider = {"npm": "@ai-sdk/anthropic"|"@ai-sdk/openai"|"@ai-sdk/openai-compatible"|"@ai-sdk/google"}`, which maps 1:1 onto `/messages`, `/responses`, `/chat/completions`, `generateContent`. It is **not** derivable from the model family (`minimax-m2.5/m2.7/m3` and `qwen3.8-flash` are all Anthropic-format).
→ Add `models` as first-class metadata on a profile: `{ id, protocol, contextWindow, maxOutput, cost, capabilities, reasoningOptions, releaseDate, source }`, resolve protocol per model, and keep the profile-level protocol only as the default.

**C1.2 · Live model discovery, with a real cache.** Adopt the opencode pattern, which we can copy in shape without copying code:
- Primary source `https://models.dev/api.json` (provider-id-keyed object; ~4.6 MB, **gzip ≈ 458 KB**, and `If-None-Match` returns **HTTP 304 with 0 bytes** — so conditional GET + compression makes refresh nearly free).
- Cache in `{userData}/models-cache.json` with an mtime TTL (~5 min) and a background refresh (~60 min); ship a **build-time snapshot** as the offline fallback; fetch order = disk → snapshot → network.
- Guard the fetch: the top level is an object, not `{providers:[…]}`; there is **no per-provider endpoint** (`/anthropic.json` returns 200 with the SPA's HTML — always check `Content-Type`); `cost` is optional and `limit.context` can be `0`.
- Attribution: repo is MIT but **data-usage terms are undocumented** → keep it a runtime cache, never a shipped fork, and attribute it in `THIRD-PARTY-NOTICES.md`.

**C1.3 · Fix `GET {base}/models` properly.** The existing parser handles only `data[]` and `models[]`, so it silently returns `[]` for Together AI (bare array), Mistral (bare array), Cloudflare (`result[]`), and Open WebUI — and then reports it as the *user's* misconfiguration. Accept `data[]`, `models[]`, `result[]`, and a bare array; filter to chat-capable models (OpenAI's list is ~130 ids including embeddings/tts/whisper); keep **free-text model entry as a permanent first-class fallback** (required for Azure deployments, GLM, GitHub Models, and every gateway with no discovery endpoint).
Also: **`/models` on `opencode.ai` needs no auth** (verified 200 for both Zen and Go) and works through the existing `listOpenAIModels()` — but Zen is intermittently slow (two probes timed out at 20 s and 60 s before succeeding in 0.8 s), so **raise the 15 s timeout to 30 s plus one retry**.

**C1.4 · Preferred providers first.** Pin **OpenCode Go** and **DeepSeek official** at the top of the catalog with first-class treatment: live `/models`, reasoning-effort control, real context window, real pricing, and one-click "test connection". Send the `User-Agent` and `x-opencode-session` headers OpenCode's docs ask for (currently omitted).

**C1.5 · Fix the freshness bugs the catalog causes today.**
- `deepseek` default is `deepseek-v4-flash`, which the provider now **retires/redirects**. Default → the current live id, and never hard-code a retired alias in the default path again.
- `openai`/`anthropic`/`google` defaults name model ids that do not exist at those providers.
- `opencode-zen`'s list is stale in **both** directions (missing new ids; listing two ids not in the live response). Replace hard-coded lists with discovery + snapshot.
- Do **not** derive "newest model" from `/models`'s `created` field — it is `Math.floor(now)` computed per request.

**C1.6 · Delete the hard-coded cost table.** `src/components/weportAi/WeportAiPanel.tsx:160-174` hard-codes DeepSeek prices and `estimateCost()` applies them to **every** provider, so the displayed cost is wrong by 3–6× on DeepSeek itself and meaningless elsewhere. Replace with model metadata from the catalog; render **`N/A`, never `$0.00`**, when pricing is unknown.

**C1.7 · Per-model context window.** `weportAiContextWindow` is one global value defaulting to `1 000 000`, so the context meter reads artificially low for every 128k–200k model, and `compressOverflow` uses a fixed 120 000-char cap rather than a fraction of the real window. Drive both from the active model's metadata. Also pass `maxOutputTokens` on the main call path — it is declared but never sent, so Anthropic silently falls back to a hard-coded 32 768.

**C1.8 · Tests.** There are currently **zero** tests under `electron/services/ai/`. Add unit tests for: model-list parsing across all five envelope shapes, per-model protocol resolution, catalog merge/precedence, cache TTL/304 handling, and cost computation. This is a prerequisite for touching the layer at all.

### 4.2 C2 · Cache-hit rate: from ~95 % to 99 %+
**Diagnosis (I read the code; the ceiling is by design).**
- `weportAiService.ts:2121-2132` caps the per-step tool budget so the fresh suffix stays ≈ 1/21 of the reusable conversation, with the comment *"~95.5 % target"*. Your live UI shows **95 %** — the code is hitting the number it was written to hit.
- `weportAiService.ts:2296-2305` pushes the `compressed` digest as the **second message**, and `:2011` grows it monotonically (`compressed = compressed + '\n\n' + digest`). Because prefix caching requires a byte-identical prefix, **every compaction rewrites the head and invalidates the entire cached suffix.**
- `weportAiConversationLimit` is **40** messages, so compaction fires on nearly every turn → the cache is reset on nearly every turn.
- The good foundations are already there and must be preserved: a stable 120-line `SYSTEM_PROMPT`, `toOpenAiTools()` sorting by name and canonicalising JSON key order, the per-run freeze of tool definitions + request shape, and strictly append-only in-run history.

**Target architecture (to be finalised against the DeepSeek-harness minimal-mode study now in flight):**
1. **Never rewrite the head.** Compaction emits its digest as a **new message appended at the tail**, so everything before it stays byte-identical and cached. A true prefix reset becomes a rare, explicit, amortised "epoch rollover" — not a per-turn event.
2. **Raise `conversationLimit`** and drive it from the real context window rather than a fixed 40.
3. **Remove the self-imposed 1/21 suffix cap** and instead bound the suffix by *usefulness* (per-tool result budgets, stratified sampling over raw dumps) so the miss ratio falls as the run gets longer, rather than being pinned at 1/21.
4. **Amortise turn boundaries.** A new user turn should append, not replace; the system prompt + tool block + prior transcript stay a warm prefix for step 1 of the next turn.
5. **Freeze everything volatile out of the prefix**: no timestamps, no "current time", no session listings, no per-turn UUIDs, no conditional tool sets inside a chat. Tool enable/disable takes effect on the next epoch.
6. **Instrument honestly.** Report cache-hit rate as `Σ cache_hit / Σ prompt_tokens` over the run **and** the per-step steady-state rate separately, so the metric cannot be gamed by capping the suffix. Add a debug overlay showing the exact byte prefix that changed between two consecutive requests — that single tool makes this class of bug impossible to reintroduce.
7. **Verify with a long-task harness:** a scripted ≥100-step investigation that asserts steady-state hit rate > 99 % and that a mid-run compaction does **not** drop the immediately following step below ~99 %.

`SYSTEM_PROMPT` line 167 says *"running inside the Weport harness on this Windows machine"* — it is sent on macOS and Linux too. Make platform text accurate or remove it (it is inside the cached prefix, so any change to it is a one-time epoch cost).

## 5. Workstream D — DROPPED (WePort free-token provider)

> **DROPPED by user decision 2026-09-13.** You will send friends a plain API key directly, so
> there is no gateway, no activation codes and no quota service. Everything below is retained
> only as a design record for a possible future version. **None of it is implemented in v1.0.**
> Consequence for the provider work in §4: nothing special is needed for the invited-user path —
> they simply configure OpenCode Go or DeepSeek as an ordinary provider profile like anyone else.

**Security model — the non-negotiable part: no upstream key ever ships in the app.**
```
user redeems activation code  →  gateway issues a device-bound token
app calls gateway            →  gateway holds the real upstream key
gateway enforces daily quota →  gateway proxies to OpenCode Go / DeepSeek
```
**Implementation:**
1. New `weport-gateway/` service in-repo (Node, deployable to Railway; mirrors the shape of the reverted `weclone-server`): endpoints for redeeming a code, issuing/refreshing a device-bound token, a daily-quota ledger, and a read-only streaming chat proxy. Deployable but **not deployed** by me — needs your credentials.
2. **Activation codes** are minted by you, single-use, with an optional expiry and an optional per-code quota; redeeming binds the code to a device fingerprint (hashed, not raw hardware IDs).
3. **Quota** is enforced and accounted server-side per token per UTC day, default 50 000 000 tokens; soft-warn at 80 %, hard-stop at 100 % with a clear in-app message and a reset countdown.
4. **Admin surface**: a tiny page behind a single `ADMIN_TOKEN` (list users, mint/revoke a code, adjust a quota, kill a token) **and** matching HTTP calls, so you can manage it from a phone while talking to someone on WeChat.
5. **App side**: a first-class "WePort" provider entry that is *visible but inert* for the general user base — it only becomes usable after a code is redeemed, and there is no hint of free quota anywhere else in the UI.
6. **Non-redeemers are unaffected**: with no token, the provider shows a single line ("需要邀请码") and takes no other action. No key, no fallback, no leakage of the gateway's existence into errors.
7. **Abuse resistance**: per-device and per-code daily caps, per-IP rate limiting, request-signature validation, an upstream-model allowlist (so the free tier cannot be used to run the most expensive models), and a global kill switch.
8. **Testable end-to-end locally** with a stub upstream, so the whole flow can be demonstrated before any real deployment.

**Open (see §0):** who hosts it, which upstream, and how you prefer to mint codes.

## 6. Workstream E — WeBot (scheduled tasks)

**Model:** a WeBot task = `{ title, description, schedule, timezone, references[], enabled, catchUpPolicy, concurrency, modelOverride }`.
**Implementation:**
1. **`electron/services/weBotScheduler.ts`** — an in-app scheduler in the main process. Ticks at a bounded interval, computes due runs from persisted specs, survives app restart and machine sleep, and dispatches each run as its own agent session.
2. **Persistence** in userData (JSON, atomic write, versioned) — no new database, no migration risk.
3. **Schedule model:** daily / weekly / monthly / interval, an explicit IANA timezone, quiet hours, and a **catch-up policy** (`skip` · `run once on wake` · `run all missed`) chosen per task, defaulting to "run once on wake".
4. **Execution:** each run creates a WeportAI-style session on a dedicated agent, with the task's `references` injected as scoped context (§7) and a **per-run token/time budget**; runs are **serialised by default** with a per-task "allow parallel" toggle so a burst of tasks cannot stampede the model or the WCDB host.
5. **Reliability:** an overdue-run guard at startup, a bounded retry with backoff on transient model/DB failure, a hard timeout per run, and a per-task run history with status + duration + error.
6. **UI:** a structured task builder — title, description (with the `@` picker, §7), schedule with a human-readable preview ("每天 08:30，下次 明天 08:30"), optional group/contact selection with chips, enable/disable, and a per-task run log.
7. **Requirement honoured:** the app already hides to tray and keeps running (`close → hide`, `--background` starts hidden), so "harness running / minimized" is the existing default, not new work. Add a tray indicator when tasks are pending and a guard that warns if the user is about to fully quit with enabled tasks.
8. **Read-only policy is preserved** — no WeBot task can send anything (consistent with `AGENTS.md`).

## 7. Workstream F — `@`-mention chat picker (WeportAI + WeBot)

1. **Shared component** `src/components/reference/ReferencePicker.tsx`, used by both the WeportAI input bar and the WeBot description field.
2. Typing `@` opens a popup listing sessions **concisely** — avatar, display name, 群聊/私聊/公众号 badge, member count for groups — with fuzzy search over name/remark/alias/wxid, keyboard-first (↑/↓/Enter/Esc/Tab), and virtualised rendering so a 5 000-session account stays instant.

4. **Injection is a scoped hint, not a data dump** (decision 8): the agent receives "the user scoped this task to these sessions" and reads them through its existing tools when relevant. This is what keeps 99 % cache hits possible and avoids paying tokens for the same group on every turn.
5. Backed by the existing `chat.getSessions()` + contact cache (already warmed at startup by `warmupContactNames`), so no new WCDB calls are needed for the list itself.
6. Accessibility: full keyboard operation, correct ARIA combobox semantics, and no focus trap leak into the chat input.
