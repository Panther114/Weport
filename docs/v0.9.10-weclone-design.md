## 1. 总览 / Goals & Non-Goals

### 1.1 目标
- **一键克隆**：用户在 Weport 应用内点击“生成人格克隆”，本地读取全部聊天历史，生成 3–5 份结构化 MD，脱敏后上传至 Railway 私有服务；生成后可直接在应用内与克隆对话，效果如同本人。
- **隐私优先**：身份证、住址、手机号、银行卡、密码等 PII 必须移除；默认私密，支持删除即焚毁服务端数据。
- **Railway 一键部署**：服务端极简内存（<100 MB），仅暴露 WeClone 聊天服务，不暴露 httpService 5031 / MCP 5032 等本地能力。
- **人格保真**：严格拒答敏感/亲密关系类问题，但**不**对脏话/口癖/黑话做二次过滤——保留本人语气。

### 1.2 非目标
- 不做服务端用户体系/社交/评论
- 不在服务端存原始微信数据库，仅存脱敏后文本 + 生成的 MD
- 不在 Railway 上暴露任何本地 WCDB/文件系统能力

### 1.3 架构总览
```
┌─────────────────────────────────┐      ┌──────────────────────────────┐      ┌──────────────────────────┐
│  Electron Client (Weport)       │      │  Railway Server              │      │  Website (Public)        │
│  ─────────────────────────────  │      │  weclone-server (Node)       │      │  Static SPA              │
│  • React: WeClonePage.tsx       │      │  • Fastify + SQLite meta     │      │  • Vite React            │
│  • Electron: weCloneService.ts  │─HTTPS┼─▶• /api/weclone/*            │◀────▶│  • /browse, /c/:id       │
│  • weportAiService (reuse)      │  TLS │  • /public browse + chat     │      │  • /share/:secret        │
│  • PII filter (regex+LLM)       │      │  • LLM proxy (stream)        │      │  • Chat UI (stream)      │
│  • Cursor scan chatService      │      │  • BM25 retrieval            │      │  • No upload             │
```

**数据流：** `chatService.getSessions → cursor scan → PII regex → LLM 二次脱敏 → 生成 MD (via weportAiService) → 压缩上传 → 服务端落盘 → 索引 → Chat (检索+LLM)`

## 2. 客户端生成管线 (Electron)

### 2.1 读取全部历史 — 游标扫描 (Cursor Scan, Batched)

**复用现有能力，不新增 native 依赖：**

- **入口：** `chatService.getSessions()` → 全部 `username` 列表（含 `@chatroom` 群聊、私聊、公众号过滤）。已在 `v0.9.6` 支撑全量导出。
- **游标：** `wcdbService.getMessageCursor / getNextMessages` 已在 `weportAiService` 的 `read_session_messages` 工具中使用。WeClone 复用同一套 `messageCursors`（LRU 8 会话、batch 50），但 WeClone 侧 **串行 + 限并发 2**，避免 WCDB host 串行队列拥塞。
- **分页策略：**
  ```ts
  // 伪代码
  for (const sid of sessionIds) {
    let cursor = await wcdbService.openMessageCursor(sid, { ascending: true });
    while (true) {
      const { messages, hasMore } = await wcdbService.getNextMessages(cursor, 500);
      // 500/批，单会话 150k 上限截断（与 wordFrequency 对齐）
      // 流式管道：PII regex → 内存 buffer → 分块落临时 JSONL
      if (!hasMore || total > 150_000) break;
    }
    await wcdbService.closeMessageCursor(cursor);
  }
  ```
- **性能预算：**
  - 100k 消息 ≈ 25–40 MB 文本，扫描 8–15s（本地 WCDB，无网络）。
  - 1M 消息：分会话串行，进度条 + `exportTaskControlService` 复用（taskId、pause/cancel、progress 事件）。
  - **禁止**一次性 `getMessages(offset, limit)` 全量加载到 renderer — 必须 main process 流式处理，renderer 仅收进度。

**与 export orchestrator 的关系：** 复用 `exportTaskControlService` 的 task 生命周期与 `export:exportSessions` 的 `onProgress` 通道，新增 `weclone:generate` 通道，避免与导出冲突（互斥锁）。

### 2.2 复用 weportAiService — 同配置、不同 System Prompt

- **配置复用：** 直接读取 `ProviderProfileService.getActive()` → `baseUrl / apiKey / model / protocol`，与 WeportAI 完全一致。用户无需二次配置。
- **隔离点：**
  - 新增 `weCloneService.buildWeClonePrompts()` 返回专用 `systemContent`，不污染 WeportAI 的 `SYSTEM_PROMPT`。
  - `WeClone` 调用走 `getProviderAdapter(profile).streamChat(...)` 同一适配层，支持 DeepSeek / OpenAI / Anthropic / 自定义 OpenAI-compat。
  - **Token 预算：** WeClone 生成阶段独立 `AbortController`，与 `weportAiService.running` 隔离；`weportAiMaxTokens` / `weportAiContextWindow` 复用。
- **Prompt 设计（见 2.3）：** 生成器 prompt 强调“提炼人格、禁止照搬 PII、保留口癖”；聊天 prompt 强调“拒答敏感、私密关系，但保留脏话/语气”。

### 2.3 要生成的 MD 文件 (3–5 份，建议 4 份)

| # | 文件 | 内容 | 来源 | 用途 |
|---|------|------|------|------|
| 1 | `profile.md` | 人格画像：性格、说话风格、口癖、表情包偏好、作息、兴趣、价值观、雷区 | 全量历史 + `getWordFrequency` + `getDailyActivity` | Chat 时 system prompt 注入 |
| 2 | `relationships.md` | 关系图谱：密友/同事/家人、称呼习惯、互动模式、群内角色 | `getContactRankings` + `getGroupMembersPanelData` | 检索时关系上下文 |
| 3 | `knowledge.md` | 知识/经历：学校/工作/项目、常聊话题、专业术语、梗/黑话词典 | `search_messages` 主题挖掘 + `analyticsService` | 检索时 factual grounding |
| 4 | `timeline.md` | 时间线：年度大事、近期状态、最近 30 天热点（脱敏后） | `snsService.getTimeline` (可选) + `list_dates` | 防止幻觉，提供时效锚点 |
| 5 *(可选)* | `language.md` | 语料样例：20–30 条脱敏后的典型发言（保留脏话/语气，去除 PII） | 采样自 `read_session_messages` | Few-shot 语气克隆 |

- **生成方式：** 每个 MD 单独一次 LLM 调用（system + 压缩后的脱敏语料摘要），流式写入 `userData/weclone-staging/{wxid}/{md}`，失败可重试单份。
- **大小约束：** 单 MD ≤ 12k chars，全量 MD ≤ 40k，满足服务端 prompt 预算。
- **存储：** 本地 `weclone-staging` 仅作上传前缓存，上传成功后可选清理。

### 2.4 PII 过滤 — 双阶段

**阶段 A — 正则/规则 (本地, 同步, 零成本, 必须)：**

```ts
const PII_PATTERNS = [
  { name: ''身份证'', re: /\b\d{15}(\d{2}[0-9Xx])?\b/g, replace: ''[身份证]'' },
  { name: ''手机号'', re: /\b1[3-9]\d{9}\b/g, replace: ''[手机号]'' },
  { name: ''银行卡'', re: /\b\d{16,19}\b/g, replace: ''[银行卡]'' }, // 需配合 Luhn 校验降低误伤
  { name: ''邮箱'', re: /\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b/g, replace: ''[邮箱]'' },
  { name: ''住址'', re: /(省|市|区|县|镇|街道|小区|栋|单元|号|楼|室).{0,12}\d+号?/g, replace: ''[住址]'' },
  { name: ''密码/密钥'', re: /(密码|passwd|pwd|密钥|token|secret)[\s:：]{0,3}[^\s]{6,}/gi, replace: ''[敏感信息]'' },
  { name: ''车牌/证件'', re: /\b[A-Z]{1,2}\d{5,6}\b/g, replace: ''[证件]'' },
];
function regexFilter(text: string): { text: string, hits: string[] } { /* ... */ }
```

- 命中即替换，不删除上下文语义。
- 银行卡加 Luhn 校验，避免将普通长数字误伤。
- 住址用关键词窗口截断，避免全段删除。

**阶段 B — LLM 二次脱敏 (异步, 抽样)：**

- 对 **已通过 regex 的文本 + 生成的 MD** 再做一次 LLM 审查：
  ```
  System: 你是 PII 审查器。输入是脱敏后的聊天摘要，请标出残留的姓名+住址组合、精确位置、财务信息、身份证/手机号等，输出 JSON {hasPII, spans}。不要改写原文。
  ```
- 命中 spans → 本地二次替换 → 人工确认（UI 展示“发现 3 处疑似 PII，已移除”）。
- **成本控制：** 仅对 MD + 采样 5% 原始消息做 LLM 二审，不对全量消息二审（否则 token 爆炸）。

**阶段 C — 人工复核 (UI)：** 上传前展示 `profile.md` 预览 + PII 命中清单，用户可手动编辑。

### 2.5 上传 Payload 结构

```json
{
  "meta": {
    "wxid": "wxid_xxx",
    "displayName": "昵称（脱敏后）",
    "knowledgeCutoff": "2026-08-23",
    "createdAt": 1724428800000,
    "clientVersion": "0.9.10",
    "messageCount": 128432,
    "sessionCount": 312
  },
  "mds": {
    "profile.md": "# ...",
    "relationships.md": "# ...",
    "knowledge.md": "# ...",
    "timeline.md": "# ..."
  },
  "chunks": [
    { "id": "c_00001", "sid": "wxid_aaa", "ts": 1724400000, "text": "脱敏后消息..." },
    { "id": "c_00002", "sid": "xxx@chatroom", "ts": 1724401000, "text": "..." }
  ],
  "visibility": "private"
}
```

- `chunks` 为 **脱敏后** 的消息分块（见 3.2），单块 ≤ 800 chars，`chunks` 总大小建议 ≤ 20 MB（Railway 内存友好，服务端可流式落盘）。
- 上传方式：`POST /api/weclone/upload`，`Content-Type: application/json`，`Authorization: Bearer <wecloneToken>`（见 4），`Body` 建议 `gzip`（Fastify 需启用 `fastify-compress` 或客户端 `Content-Encoding: gzip`）。
- 上传前客户端对 `chunks` 做 `fzstd` 可选压缩（复用 `fzstd` 依赖），服务端解压。

## 3. 服务端设计 (weclone-server) — 极简内存

### 3.1 框架选择

| 选项 | 内存 | 流式 | 生态 | 结论 |
|------|------|------|------|------|
| **Fastify** | ~40–60 MB RSS (Node 18) | 原生 `reply.raw` stream、@fastify/compress、@fastify/cors | 轻量、schema 校验快 | **推荐** |
| Express | ~55–75 MB | 需手动 `res.write` | 中间件多但冗余 | 可行但稍重 |

**选择 Fastify**：`fastify@4 + @fastify/multipart + @fastify/cors + @fastify/rate-limit`，单进程，无 clustering。

### 3.2 存储

- **文件系统 JSON + SQLite 元数据 (混合)：**
  ```
  data/
    meta.db              # SQLite 1 表: clones(id, ownerTokenHash, displayName, visibility, secret, cutoff, createdAt, chunkCount, mdSize)
    blobs/
      <cloneId>/
        meta.json
        profile.md
        relationships.md
        knowledge.md
        timeline.md
        chunks.jsonl     # 每行一个 chunk {id, sid, ts, text}
        index.json       # BM25 倒排（可选，懒生成）
  ```
  - **为何不用纯 SQLite FTS：** `chunks.jsonl` 追加写入快、内存零拷贝；`meta.db` 仅存索引与权限，避免将大文本塞进 SQLite 导致内存峰值。
  - **为何不用 Postgres/Redis：** Railway 免费/入门档无外部依赖，单容器可移植。

- **分块 (Chunking)：**
  - 客户端已分块 800 chars / chunk，服务端不再重分块。
  - 检索时按 `sid + ts` 排序，取 topK 8–12 块注入 prompt。

- **懒加载：**
  - 启动时不加载任何 clone 的 chunks；请求时 `fs.createReadStream` + `readline` 流式扫描。
  - `index.json` 首次聊天时懒生成（BM25 倒排，见 3.3），缓存在内存 LRU (max 5 clones, ~5 MB)。

### 3.3 检索策略

- **BM25 (轻量) 优先：** 使用 `wink-bm25-text-search` 或手写 200 行 BM25（无依赖、零 native 编译）。按 `text` 字段建索引，停用词复用 `wordFrequency.ts` 的 CJK 二元分词 + 停用词表（服务端 JS 移植）。
- **Fallback：** 若 `wink-bm25` 未命中，退化为 `simple search`：`chunks.filter(c => c.text.includes(keyword))` 取前 8。
- **TopK 注入：** `profile.md + relationships.md + 检索到的 chunks(8) + timeline.md 摘要` 拼成 `system + context`，总 prompt ≤ 8k tokens。
- **无向量库：** 不引入 `sqlite-vec` / `pgvector` / `transformers.js`，避免 native 编译与 100 MB+ 模型内存。

### 3.4 LLM 代理

- **透传：** 服务端不存任何 LLM key，客户端上传时可附 `llmConfig`？**否** — 服务端 LLM key 由 **Railway 环境变量** 配置（见 7），统一代理，避免客户端 key 泄露。
- **提供商：** 默认 `DeepSeek` OpenAI-compat (`https://api.deepseek.com/chat/completions`)，可通过 `WEclone_LLM_BASE_URL / WEclone_LLM_MODEL` 覆盖。
- **流式：** `POST /api/weclone/:id/chat` → 服务端 `fetch` LLM with `stream:true` → `reply.raw.write` SSE (`text/event-stream`) 转发给客户端/网站。

### 3.5 认证 / 限流 / 流式

- **Auth：**
  - `ownerToken`：客户端生成 `randomUUID + hash`，`Authorization: Bearer <token>` 持有者即 owner，可 list/get/delete/updateVisibility。
  - `secret`：link-only 可见性时生成 16-hex，作为 `?secret=` query 鉴权。
  - 不做用户注册/登录，保持极简。
- **Rate limit：** `@fastify/rate-limit` → `chat` 接口 20 req/min/IP，`upload` 5 req/hour/IP。
- **Streaming：** Fastify `reply.raw.writeHead(200, {''Content-Type'': ''text/event-stream''})`，每 `delta` 一次 `write(''data: {...}\n\n'')`，结束 `write(''data: [DONE]\n\n'')`。

### 3.6 内存预算 (<100 MB RSS)

```
Node 18 + Fastify        ~30 MB
SQLite (meta.db)         ~2 MB
LRU index (5 clones)     ~5 MB
单请求 chunks 扫描       ~2–4 MB (流式)
LLM proxy buffer         ~1 MB
Total steady RSS         ~45–65 MB
Peak (upload 20 MB)      ~75–85 MB (流式落盘，不全量驻留)
```

- 启动参数：`NODE_OPTIONS=--max-old-space-size=256`，`UV_THREADPOOL_SIZE=4`。

## 4. API 规范

**Base:** `https://<railway>.up.railway.app`  
**Headers:** `Authorization: Bearer <ownerToken>` (除 public-browse / link-access)  
**Content-Type:** `application/json` (upload 支持 `gzip`)

| Method | Path | Auth | Body/Query | 响应 |
|--------|------|------|------------|------|
| `POST` | `/api/weclone/upload` | Bearer | `{meta, mds, chunks, visibility}` | `{success, id, cutoff}` |
| `GET` | `/api/weclone/list` | Bearer | — | `{clones: [{id, displayName, cutoff, visibility, createdAt}]}` |
| `GET` | `/api/weclone/:id` | Bearer **或** `?secret=` (link-only) | — | `{meta, mds, visibility}` (不含 chunks) |
| `DELETE` | `/api/weclone/:id` | Bearer (owner) | — | `{success}` + 服务端 `rm -rf blobs/<id>` + `DELETE FROM meta` |
| `PATCH` | `/api/weclone/:id/visibility` | Bearer | `{visibility: ''private''|''public''|''link'', secret?}` | `{success, visibility, shareUrl?}` |
| `POST` | `/api/weclone/:id/chat` | Bearer **或** public/link 匿名 | `{messages: [{role, content}], stream?: boolean}` | SSE stream 或 `{reply}` |
| `GET` | `/api/weclone/public` | 无 | `?q=&limit=20&offset=0` | `{clones: [...]}` (仅 visibility=public) |
| `GET` | `/api/weclone/:id/share` | `?secret=` | — | 同 `GET /:id` 但 via secret |
| `GET` | `/health` | 无 | — | `{ok, version, uptime}` |

**错误：** `{success:false, error:''msg''}` + HTTP 401/404/429/413。

**流式 Chat 协议 (SSE):**
```
event: delta
data: {"delta":"你好"}

event: done
data: [DONE]
```

### 4.1 关键实现细节

- `upload` 需校验 `chunks` 单请求 ≤ 25 MB，`mds` 单份 ≤ 20k，超时 30s。
- `list` 按 `ownerTokenHash` 过滤（SHA-256 hash 存储，不存明文 token）。
- `public` 列表默认按 `createdAt DESC`，`q` 走 BM25 的 `displayName + profile.md` 摘要匹配。

## 5. 网站 (Website)

**决策：静态 Vite React 内嵌于 `weclone-server/public`，不单独部署。**

- **理由：** Railway 单服务暴露，减少运维；`fastify-static` 直接托管 `public/`，零跨域；符合“仅暴露 weclone 服务”。
- **技术：** `Vite + React + react-router` 构建产物 `dist/` → `weclone-server/public/`，`fastify-static` 挂载 `/*` fallback 到 `index.html`（SPA）。
- **页面：**
  - `/` — Landing + 公开克隆浏览 (`GET /api/weclone/public`)
  - `/c/:id` — 公开克隆对话 (public)
  - `/share/:id?secret=xxx` — 链接访问 (link-only)
  - `/chat/:id` — Owner 私聊 (需 token 输入框，localStorage 存)
  - **上传不在网站** — 仅 Weport 客户端可上传（防滥用/防 PII 泄露）。
- **Chat UI：** 复用 Weport 的 `weportAiService` 流式渲染逻辑（`marked` + SSE），但精简为单会话、无工具调用。
- **构建：** `weclone-server` 的 `npm run build` 调用 `vite build` 生成 `public`，Dockerfile 仅复制 `public`。

**替代方案 (Rejected)：** 单独 Vercel 前端 → 需跨域 CORS、双部署、双域名，不符合极简。

## 6. 安全与隐私

### 6.1 PII 过滤三阶段

1. **Regex 本地 (必过)：** 见 2.4 阶段 A，100% 本地执行，无网络。
2. **LLM 二审 (抽样)：** 见 2.4 阶段 B，对 MD + 5% 采样消息二审，命中即阻断上传并提示。
3. **服务端复核 (可选)：** 上传后服务端对 `mds` 再跑一次 regex，防止客户端绕过。

### 6.2 拒答 Prompt (Sensitive / Relationship)

**Chat System Prompt 片段 (服务端注入，不可被用户覆盖)：**

```
你是 “{displayName}” 的人格克隆，基于以下资料回答...
- 严格拒答：身份证、住址、手机号、银行卡、密码、精确位置、私密关系评价（如“你和 X 是否分手/出轨”）、医疗/法律建议。遇到此类问题，回复：“抱歉，这个问题涉及隐私/敏感信息，我不能回答。”
- 允许：脏话、口癖、黑话、玩笑、吐槽 — 保持本人语气，不要做道德说教或内容过滤。
- 不要编造未在资料中的事实，证据不足时说“记不清了”。
```

- **实现：** 服务端在每次 `chat` 前将该拒答指令 **前置** 于 `profile.md`，LLM 无法被用户 `messages` 覆盖（取最后一条 user 之前插入 system）。
- **No guardrails for profanity：** 显式告知 LLM “不要过滤脏话”，并在 `temperature: 0.9` 保留多样性。

### 6.3 数据擦除

- `DELETE /api/weclone/:id` → `fs.rm(blobs/<id>, {recursive:true})` + `DELETE FROM meta WHERE id=?`，返回前 `fsync`。
- 定时任务（可选）：`visibility=private` 且 90 天未访问的 clone 可标记为过期（暂不自动删，需 owner 手动）。
- **日志：** 不记录 `chunks` 内容，仅记录 `id + 行为 + IP hash`。

### 6.4 Token 处理

- `ownerToken` 客户端生成 `crypto.randomUUID()` + `sha256` 后存 `configService` (`wecloneToken`，`electron-store` + `safeStorage` 加密，复用 `mcpToken` 模式)。
- 服务端仅存 `tokenHash` (SHA-256)，不存明文；鉴权时 `hash(req.token) === stored`。
- `secret` 16-hex，`visibility=link` 时生成，`private/public` 时清空。

## 7. Railway 部署

### 7.1 Dockerfile vs Nixpacks

- **选择 Dockerfile (推荐)：** 可控、可复现、镜像小（`node:18-alpine` ~80 MB）。
  ```dockerfile
  FROM node:18-alpine
  WORKDIR /app
  COPY weclone-server/package.json weclone-server/pnpm-lock.yaml* ./
  RUN npm ci --omit=dev
  COPY weclone-server/ ./
  RUN npm run build   # vite build → public/
  EXPOSE 3000
  HEALTHCHECK --interval=30s --timeout=5s CMD wget -qO- http://127.0.0.1:3000/health || exit 1
  CMD ["node","dist/server.js"]
  ```
- **Nixpacks：** 零配置但不可控、镜像大 (~300 MB)，不推荐。

### 7.2 环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `PORT` | `3000` | Railway 注入 |
| `WECLONE_DATA_DIR` | `./data` | 持久化卷 `RAILWAY_VOLUME_MOUNT_PATH` |
| `WECLONE_LLM_BASE_URL` | `https://api.deepseek.com` | LLM 代理目标 |
| `WECLONE_LLM_API_KEY` | — | 服务端 LLM key (Railway Variables, 加密) |
| `WECLONE_LLM_MODEL` | `deepseek-chat` |  |
| `WECLONE_MAX_UPLOAD_MB` | `25` |  |
| `WECLONE_RATE_LIMIT_CHAT` | `20` | per min |
| `CORS_ALLOW_ORIGINS` | `*` | 生产建议收敛 |

### 7.3 健康检查 & 一键部署

- **Healthcheck：** `GET /health` → `{ok:true, version, uptime}`，Railway `healthcheckPath: /health`。
- **One-click Deploy：**
  1. 仓库根 `railway.json` + `weclone-server/Dockerfile`。
  2. 按钮：`[![Deploy on Railway](https://railway.app/button.svg)](https://railway.app/template/XXXX)` → 模板指向 `weport/weclone-server`。
  3. 用户仅需填 `WECLONE_LLM_API_KEY`，其余默认。
- **仅暴露 WeClone：** `weclone-server` 只监听 `PORT`，不监听 5031/5032；`httpService`/`mcpService` 保持 `127.0.0.1` 本地绑定，不打包进 `weclone-server`。

### 7.4 持久化

- Railway Volume 挂载到 `WECLONE_DATA_DIR`，`meta.db` + `blobs/` 持久化，重启不丢。
- 备份：Volume 快照由 Railway 提供，无需应用层额外备份。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| **PII 漏网** | 法律/隐私事故 | 双阶段过滤 + 人工预览 + 服务端复核；上传前展示 hits 清单，用户确认后才上传 |
| **大历史 OOM** | 生成时主进程崩溃 | 游标批处理 500/批 + 流式 JSONL 落盘 + 单会话 150k 截断 + 进度/取消 |
| **LLM 成本/限流** | 生成失败或费用高 | MD 生成 4 次调用 + 5% 采样二审，预估 30k–60k tokens/次生成；服务端限流 + 客户端重试 |
| **Railway 内存超限** | OOM 重启 | Fastify 单进程 <65 MB 稳态；upload 流式落盘；`--max-old-space-size=256`；Volume 持久化 |
| **BM25 效果差** | 克隆答非所问 | TopK 8–12 + profile.md 常驻 + 无命中时 fallback 全文 simple search |
| **Prompt 注入绕过拒答** | 敏感信息泄露 | 服务端前置拒答 system，不接受客户端 system 覆盖；输入过滤 `ignore previous instructions` |
| **Token 丢失** | 无法管理克隆 | `wecloneToken` 存 electron-store + safeStorage，可导出/重置；服务端提供 `?secret` 备用 |
| **并发上传/删除竞态** | 数据不一致 | `meta.db` 事务 + `fs.rm` 原子；`upload` 与 `delete` 同 id 互斥锁 |
| **脏话被误过滤** | 人格失真 | Chat prompt 显式“保留脏话/口癖”，`temperature 0.9`，不走二次 moderation |
| **仅暴露 WeClone 的合规** | 误暴露 5031/5032 | `weclone-server` 独立仓库/目录，仅监听 `PORT`；`httpService`/`mcpService` 保持 127.0.0.1，不打包 |

## 10. 实施里程碑 (建议)

1. **M1 — Client 管线 (3–4d)**：`weCloneService` 游标扫描 + PII regex + `weportAiService` 4×MD 生成 + 本地预览
2. **M2 — Server 最小闭环 (3d)**：Fastify + SQLite meta + FS blobs + upload/list/get/delete + 健康检查 + Dockerfile
3. **M3 — Chat 检索 (2d)**：BM25 + LLM proxy SSE + 拒答 prompt
4. **M4 — Visibility & Website (2d)**：private/public/link + Vite 静态站 + public browse
5. **M5 — 集成 & QA (2d)**：`WeClonePage` + IPC + 端到端 demo (WEPORT_V09_DUMP 复用模式) + Railway 一键部署验证
