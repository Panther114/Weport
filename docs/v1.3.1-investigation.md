### #50: reverse quote lookup and regex triggers

Reader quote blocks currently display the quoted sender and content; they do not expose reverse references. `chatService.ts` parses `<refermsg>`, and media quotes can resolve `<svrid>`, but a durable reverse-reference relationship is not exposed to Reader. A reliable implementation needs the referenced server ID as an exact string and the quoting message's account/session/database/table/local identity. Existing physical provenance must be retained; duplicate server IDs must not be collapsed or resolved by text similarity. A bounded initial query and an incremental reverse-reference index can support complete lookup without rescanning the history on every click. Missing or ambiguous targets should remain explicit.

WeBot currently accepts time schedules only. The repository already has `chatService.addDbMonitorListener`, suitable for incremental message discovery. Regex triggers should use that data path, with account binding, validation, bounded matching, a durable message cursor/deduplication key, cooldown/debounce and controlled concurrency. Reusing the notification `onPush` outlet would make triggers depend on notification enablement, mute filtering and notification suppression. Existing self-sent notification filtering must remain intact. Runs require the app to be running and a live database connection; a read-only imported snapshot cannot supply real-time events.

### #49: recording compatibility

`electron/windows/notificationWindow.ts:728` implements `setLiveGlassProtection`, which calls `BrowserWindow.setContentProtection`. This excludes the popup from capture so the glass pipeline does not capture its own output. The optional native-glass implementation also documents capture exclusion, so merely switching renderers would not resolve the underlying conflict.

[Electron documents](https://www.electronjs.org/docs/latest/api/base-window#winsetcontentprotectionenable-macos-windows) that Windows content protection uses `WDA_EXCLUDEFROMCAPTURE`. [Nvidia documents](https://nvidia.custhelp.com/app/answers/detail/a_id/5602/kw/manuals/related/1) that protected content can stop desktop Instant Replay. Connecting these facts to the report is an inference, not a completed GPU reproduction. The report's embedded image could not be fetched by the web tool; the issue body was retrieved successfully.

A feasible fix is a recording-compatible mode that disables both protected-window rendering and live desktop capture, using a static/CSS surface or native OS notification instead. Disabling only content protection risks recursive glass capture. The same handling should cover chat and WeBot notifications. Test Instant Replay before, during and after repeated notifications on Nvidia hardware, alongside window geometry, interactions and existing glass behavior.

### #48: image quality

Three existing file tiers are recognized: original `_h.dat`, display `.dat`, thumbnail `_t.dat`. Export already requests `excludeThumbnail: true`, while Reader's `readerSource.ts:279` does not. Reader's `MessageBlocks.tsx:173` uses the same image cache for bubbles and the full-size viewer, and a cache hit returns without requesting a better tier. This can keep a thumbnail in the viewer after a better local image becomes available. The decoder's ordinary promotion path still looks specifically for an HD/original result; the explicit non-thumbnail path has the broader three-tier upgrade logic.

Feasible work: separate preview and full-view quality intent, request the best available local variant in the viewer and downloads, invalidate/upgrade low-quality cache entries, preserve exact image identity, and expose actual dimensions/tier when only a thumbnail is available. Export needs a targeted reproduction because it already requests better tiers. Existing WXGF tests confirm a thumbnail fallback when HEVC conversion is unavailable; that is another possible cause, not an established diagnosis for this reporter. Do not upscale or label a thumbnail as an original. Weport cannot obtain an original that WeChat has never downloaded through its existing local-only media interface.

## WeBot separation and historical migration

`appMain.ts:2208` creates every automated run through `weportAiService.createChat`, with `invocation: { kind: 'automation', taskId }`. `weportAiService.ts:990` returns every indexed chat. `WeportAiPanel.tsx:1034` intentionally renders automated entries with the “自动任务” prefix. The requested disappearance is therefore a storage/API ownership change, not just a label adjustment.

WeBot already has a per-task run-log menu, but it displays status, timing, errors and note references. `WeBotRun` does not persist an AI transcript ID. A dedicated run-history/transcript view can reuse this entry point while removing automated runs from all interactive AI chat lists.

The migration should preserve full messages, compacted/archive history, notes, identifiers, evidence links, task associations and timestamps in account-scoped automation storage. It needs an idempotent migration journal/backup and a verified destination before removing an entry from the interactive index. Existing `invocation` metadata identifies newer runs exactly. Git history confirms that pre-v1.2.2 runs lack that tag but include a recognizable scheduler-generated prompt; those need conservative content/metadata matching, never title matching alone. Ambiguous records cannot safely be attributed with certainty. Do not delete them or silently relocate an ordinary user chat.

Preserve historical runs whose task was deleted or whose log was trimmed: WeBot normally retains only 400 runs, while AI transcripts have separate persistence. Migration must not trim imported history through that limit. Update internal consumers such as shutdown cancellation and `review_prior_analyses`, rather than hiding the UI while leaving cross-surface retrieval and lifecycle bugs.

## Per-chat memory choice

Feasible. Add a persisted creation-time `memoryEnabled` flag, defaulting to true for new and legacy chats. The choice should appear in the new-chat flow, including the existing empty-chat reuse path. Keep per-chat working notes distinct from shared persistent memory.

Enforce the flag in the backend, not only in the prompt. Disabled chats must not read or write Markdown memory or structured claims through `list_memory_claims`, `save_memory_claim`, `list_notes`, `read_note` or `write_note`. Tool listings, file-path resolution and handlers must agree. Audit `review_prior_analyses` as another cross-chat persistence path, so the setting cannot be bypassed by retrieving prior conclusions or exposing disabled conversations as future memory. Freeze capabilities per run. Leave shared memory on disk for chats where it remains enabled.

## Minimal system prompt

Feasible. `electron/services/ai/systemPrompt.ts` currently contains about 23.6k characters across the main and automation prompts: forced spelling, language, tone, answer sections, private/group evidence hierarchy, mandatory tool order and investigation playbooks. These directly explain the reported restriction.

Simplify the default to minimal environment/capability context and tool definitions. Remove imposed response language, vocabulary, style, format, investigation sequence and mandatory memory use. Audit tool descriptions and the extra text injected by `dispatchWeBotTask`: changing `SYSTEM_PROMPT` alone leaves further output instructions active. Preserve explicitly configured user instructions. Account/file access, credential permissions, context limits and cancellation are backend operational controls and should continue to work independently of response style.

One related defect was reproduced: `weportAiService.ts:667` rewrites and persists both assistant AND user text when loading a conversation. For example, `Quote "WreportAI" literally.` becomes `Quote "WeportAI" literally.` on disk. API construction also normalizes user text. Remove this content rewriting as part of the requested cleanup; deleting the spelling rule from the prompt alone is insufficient. Existing tests tied to old prompt wording will need meaningful updates.

## Global and group analysis performance

Both have concrete improvement opportunities, but no before/after speedup was measured because implementation was explicitly deferred.

Global analysis (`GlobalAnalytics.tsx:165`) waits for all six initial requests, including word-frequency scanning, before rendering the main results. Rankings start afterward. Optional word clouds/calendars should load independently; render basic statistics when ready, retain account/source-scoped cached results across navigation, and avoid repeating connection/session inventory work. Self-sent daily statistics and calendar fallback can each scan history separately; share compatible work where semantics match. Existing aggregate caching/deduplication must be preserved.

Group selection (`GroupAnalytics.tsx:368`) eagerly requests members/counts, ranking, hours, media and a full-history 7×24 heatmap. It waits for all five before presenting members. Load the selected tab first, defer the heatmap until needed, and reuse aggregate/member enrichment work. The backend already shares native group statistics, so adding more parallel requests alone will not remove serialized native work. Group-list opening also waits for member counts, message counts and contact enrichment for every group; a staged list can display names earlier.

Verified additional defects:

1. **Cross-account cached group statistics.** `getGroupStatsCached` keys only by group/time; the heatmap cache similarly omits account identity. A synthetic test opened account A then B for the same group, confirmed B's connection, and received A's cached statistics without another native stats call. Scope keys and in-flight work to the account/database generation. The members-panel cache already includes a database/account component and must not be conflated with these unscoped caches.
2. **Ineffective word-frequency scan stopping.** After reaching 150,000 qualifying messages, the row callback returns, but `iterateSessionMessages` continues fetching remaining pages of that session. A synthetic test confirmed a second fetch after the cap. The counter also counts qualifying self-sent text, not all fetched rows.
3. **Silent analytics cursor failures.** Cursor-open failures return normally and failed later pages break the loop. Callers can then cache/report empty or partial results as success. Both cases were reproduced with synthetic cursor failures.
4. **Group-selection response race.** Code inspection shows no selection/request token check before setting results in `loadGroupData` or `reloadRanking`. A slower request for group A can replace the content after selection changes to B. This finding has not had a rendered interaction reproduction. Selecting a group also requests its ranking twice through the callback and the selection effect.

## Moments anti-delete

The exact message comes from `appMain.ts:876`: `withWriteSnapshotBody` refuses a manual database modification while a WeChat PID exists. This is an intentional safety condition. It closes the WCDB connection, copies database/WAL/SHM files and verifies stability before reopening and installing the native SNS delete-blocking trigger. Removing the PID check would not make the current raw-copy backup transactional. Existing UI checks mock these IPC handlers and do not establish live native trigger safety.

Feasible alternatives:

- Persist an account-bound pending enable/disable request and automatically perform the guarded backup and trigger installation after WeChat exits. Recheck account, opt-in, process state and trigger status; report progress through the existing global task system. No need to repeat manual setup when the trigger remains installed.
- Add an opt-in background read-only Moments archive that preserves observed post content and available media outside WeChat's database. This can run while WeChat is open and preserve already-captured posts after deletion. It cannot restore the original WeChat/server post, guarantee capture before deletion, or recover never-observed content. Full-resolution media still depends on availability at capture time.

A lossless live-database bypass is not established with the current exposed snapshot mechanism. It needs separate native transactional-backup/concurrency evidence, not removal of the warning. Never restore a copied old SNS database over a running WeChat instance.
