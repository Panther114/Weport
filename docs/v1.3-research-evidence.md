# V1.3 research evidence and inspection record

Date: 20 October 2026 (Asia/Taipei). Companion: [recommendation report](v1.3-research-report.md).

## Method and boundaries

Screened 14 external repositories/projects. Cloned 12 public default-branch snapshots into a temporary research directory outside Weport. Inspected implementation paths in seven: ChatLab, WeFlow, Karakeep, Khoj, Open WebUI, Screenpipe and the third-party WCDB wrapper. Inspected current repository inventories/removal notices for four former WeChat tools, and Yance planning contracts. Alpha was inspected through its current public release/documentation page; the linked Miyu repository returned HTTP 404.

Read selected implementation paths and relevant regression-test source, not every file. Did not run competitor applications, install their dependencies, execute their tests, compile native code, or access personal WeChat data. No comparative performance claims are established by this investigation. Public issue descriptions are reports/proposals, not verified diagnoses. This is a broad engineering comparison, not an exhaustive audit of all projects or a user-demand study.

Search was used for discovery; primary repository pages, current clones and source were used for conclusions. One discovery result described WeFlow as README-only; a fresh checkout actually contains 554 tracked files and external-component interfaces. The report uses the checkout rather than that stale description.

## Decisions from the code inspection

### Search: use the pattern, retain Weport semantics

ChatLab persists vector metadata separately from source chat databases and partitions vectors by database hash and model, with dimensions represented by separate tables. The evidence assembler re-reads source windows, expands context without crossing parent boundaries, merges overlaps and enforces token budgets. Those are useful design patterns. Its message IDs are numeric within its normalized database; Weport must preserve string-valued exact native IDs and compound database/table provenance instead of transplanting that identity scheme.

In the inspected semantic-search path, a date restriction multiplies the initial candidate pool by ten, then filters candidates in application code. This improves coverage but cannot guarantee it: if all shortlisted candidates lie outside the requested window, an in-window result ranked just beyond the shortlist is never considered. This is a static inference from control flow, not a reproduced bug report. Prefer filter-aware retrieval or explicit incomplete-coverage reporting.

Open WebUI shows lexical/vector fusion and optional reranking, but its legacy path materializes a collection and constructs BM25 using whitespace tokenization. That is a poor direct fit for Weport's large Chinese history. Learn from fusion/citation interfaces; benchmark a derived local inverted index and suitable tokenization independently. Screenpipe's FTS migration illustrates update/delete synchronization and transactional rebuilds; do not install its triggers in WeChat source databases. Any FTS tables/triggers belong only in Weport-owned derived storage.

### Jobs: retries and visibility must match committed work

Karakeep has a real SQLite queue backend with configured timeouts, retries, concurrency and retained failed-job options. Its preprocessing worker clears pending downstream states on final failure. Its backup scheduler uses an idempotency key. These patterns support Weport's existing ledgers and background task lifecycle without introducing Redis or a server stack. A queue alone does not make output commits idempotent.

ChatLab's inspected import-idempotency cache is an in-memory Map with a one-hour default TTL. Its tests cover retry/conflict/expiry, but that cache is not a durable restart guarantee. A Weport scheduled archive or digest needs a persisted run key and committed output/watermark together. Preserve existing cancellation, cleanup, source fingerprints and artifact hashes.

Khoj schedules timezone-aware jobs behind process locks. Its notification decision asks a model and defaults to notifying after errors. Weport should cheaply detect no-change runs first and avoid adding a model call merely to decide whether a completed no-op deserves a notification.

### Evidence and identity: useful intelligence requires reversible conclusions

ChatLab's evidence UI and cross-chat context lookup retain source context. Yance offers a useful explicit distinction between supporting, contradicting, correcting and invalidating evidence. Yance is planning-only: the JSON schema is a proposed contract and archived code is not a supported integration. Recommend independent implementation of dated claims and corrections, with original message anchors. Avoid inferring relationship roles from co-activity or reply volume alone.

Weport currently already has exact Reader navigation, annotations and source identity helpers. Its AI memory path resolves to a common workspace-root/memory directory rather than an account namespace. Audit account-switch behavior and add an explicit ownership/migration contract; do not label this inspection as a proven cross-account data leak.

### Native resilience: source availability does not prove substitutability

The third-party wrapper exposes a broad C ABI and platform build guide. However, the current inspected repository has no license file, ships precompiled dependencies, and contains no accepted Weport fixture parity evidence. `wcdb_get_message_by_svrid` parses the supplied ID into signed 64 bits, takes the first match and narrows the returned local ID to int32 before a second lookup. That is incompatible with assuming exact arbitrary-size IDs or rejecting reused server-ID ambiguity. `InitProtection` and authentication stubs return success; that does not establish the protections or host behavior required by Weport. Cloud report functions call an upstream HTTPS endpoint when invoked; this review did not establish that they run automatically.

Recommendation: an ABI/provenance/fixture research track only. Do not replace the accepted binary, remove host guards, change IPC, or alter the permanent pure-Node host deployment rules on the strength of this source review.

## Validation plan for a later implementation
